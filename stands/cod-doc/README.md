# Стенд cod-doc

Готовая конфигурация петли для репозитория
[`cod-doc`](https://github.com/Orange-hanter/cod-doc) — MCP-сервер и
автономный агент управления проектной документацией (Python 3.11–3.13,
~1390 тестов, ruff + mypy strict).

Здесь лежит эталон `swarm.toml` и порядок развёртывания. Каждое решение
ниже — след конкретной пробы 2026-08-26, а не вкус: разворачивать стенд
на cod-doc «как обычно» не получается четырьмя разными способами, и все
четыре молчат до середины первого прогона.

## 1. Где стенд и почему НЕ в `.claude/`

```
/Users/dakh/Git/_my/cod-doc          # рабочий чекаут владельца — рой сюда не ходит
/Users/dakh/Git/_my/cod-doc-swarm    # стенд: git worktree, ветка swarm/main
```

Первая попытка положила стенд в `cod-doc/.claude/worktrees/…` — туда его
кладёт `EnterWorktree` в Claude Code. Файлы под `.claude/` Claude Code
считает чувствительными и править отказывается: исполнитель возвращает
`dispute` вместо работы, и выглядит это как спор о постановке задачи, а
не как ловушка среды. С 2026-08-26 это ловит `swarm doctor` строкой
`[ПРОБЛ] стенд`, но выбор места всё равно за оператором.

## 2. Развернуть с нуля

```sh
CODDOC=/Users/dakh/Git/_my/cod-doc
STAND=/Users/dakh/Git/_my/cod-doc-swarm

# 1. Ветка от ЛОКАЛЬНОГО main, а не от origin/main
cd "$CODDOC"
git worktree add "$STAND" -b swarm/main main

# 2. Свой venv, версии — как у владельца (см. §4)
cd "$STAND"
"$CODDOC"/.venv/bin/python -m pip freeze --exclude-editable > stand-constraints.txt
uv venv .venv --python 3.13
uv pip install --python .venv/bin/python -r stand-constraints.txt
uv pip install --python .venv/bin/python -e '.[dev]'
uv pip uninstall --python .venv/bin/python types-PyYAML   # см. §5

# 3. Конфиг прогона
cp /path/to/zairgrush/stands/cod-doc/swarm.toml "$STAND"/swarm.toml

# 4. Спрятать имущество петли от preflight (см. §6)
cat >> "$CODDOC"/.git/info/exclude <<'EOF'
swarm.toml
.swarm/
stand-constraints.txt
EOF

# 5. Проверка
cd /path/to/zairgrush/tools/swarm
./swarm-cli --root "$STAND" doctor
```

**Ветка от локального `main` — обязательно.** В cod-doc локальный `main`
уходит вперёд и не пушится: на 2026-08-26 разрыв был 38 коммитов. Стенд,
ветвлённый от `origin/main` (умолчание `EnterWorktree`), не содержит
миграций `0024`/`0025` — задача просто не на чем стоит, а падение
выглядит как регресс работы исполнителя.

## 3. Свой `.venv`, а не симлинк на venv владельца

Симлинк ломает две вещи сразу:

1. **Он уезжает в коммит.** В `.gitignore` cod-doc написано `.venv/` — со
   слэшем, то есть про КАТАЛОГ. Симлинк для git — файл, правило его не
   покрывает, и `git add -A`, которым петля коммитит принятую итерацию,
   утащит его в историю.
2. **Гейт судил бы чужой код.** `pip install -e` прописывает ссылку на
   исходники ТОГО чекаута, где ставили. Общий venv означает, что
   исполнитель правит `$STAND/cod_doc/`, а тесты импортируют
   `$CODDOC/cod_doc/` — петля крутится вокруг кода, которого не видит.

Проверка после установки — обязательна:

```sh
.venv/bin/python -c "import cod_doc; print(cod_doc.__file__)"   # должен быть путь СТЕНДА
```

## 4. Версии инструментов закреплены по venv владельца

Гейт стенда обязан воспроизводить гейт, которому владелец верит. Свежая
установка `.[dev]` этого не делает — пины в `pyproject.toml` верхней
границы не имеют:

| | стенд «как поставится» | venv владельца |
|---|---|---|
| ruff | 0.16.4 | 0.15.15 |
| mypy | 2.3.1 | 2.1.0 |
| numpy | 2.5.2 | 2.4.6 |

Каждая строка — красный гейт на нетронутом дереве: ruff 0.16 приносит
`RUF036` (9 срабатываний), а numpy 2.5.2 роняет mypy на собственных
стабах (`Type statement is only supported in Python 3.12 and greater` —
при `python_version = "3.11"` в конфиге cod-doc). Петля, стартующая на
красном гейте, обвиняет исполнителя в чужой поломке и выжигает раунды.

Отсюда `stand-constraints.txt`: снимок `pip freeze` рабочего venv.
Обновляется вместе с ним, руками и осознанно.

## 5. Чего гейт стенда НЕ ловит: дельта с CI

Стенд равен ЛОКАЛЬНОМУ гейту владельца, и на 2026-08-26 локальный гейт
слабее CI в двух местах. Оба дефекта существуют в cod-doc уже сейчас и
оба невидимы на машине владельца:

1. **`redundant-cast` в `cod_doc/services/projection_service/_frontmatter.py:87`.**
   `cast("str", yaml.dump(...))` избыточен, когда установлен
   `types-PyYAML`. В dev-extras он объявлен (коммит 391a33a), в venv
   владельца его нет — а CI ставит `pip install .[dev]` и получит его.
   Поэтому в §2 стоит `uv pip uninstall types-PyYAML`: это ПОДПОРКА до
   починки, а не решение. Починка — снять cast (4 строки).
2. **9 × `RUF036`** (`None` не в конце union). CI ставит `pip install
   ruff` без пина, то есть латест; локально стоит 0.15.15. 8 из 9
   правятся `ruff check --fix`.

Пока это не закрыто, работа, принятая роем, может упасть в CI. Отдельно
стоит починить и сам CI: незакреплённый линтер — это движущийся гейт, а
под автономной петлёй движущийся гейт сам по себе дефект.

## 6. `swarm.toml` и `.swarm/` — в `.git/info/exclude`

`preflight` отказывается стартовать на грязном дереве, а
`changed_files()` не исключает имущество петли (`OWNED_ROOTS`). Значит
незакоммиченные `swarm.toml` и `.swarm/` — это грязь, и каждый прогон
требовал бы `--force`, то есть отключал бы саму защиту от грязного
дерева ради двух собственных файлов петли.

`.git/info/exclude` решает это без следа в репозитории: файл локальный,
общий для всех worktree, в git не попадает. Постоянное решение — две
строки в `.gitignore` самого cod-doc, но это правка чужого репозитория и
решение его владельца.

## 7. Запуск

```sh
cd /path/to/zairgrush/tools/swarm
./swarm-cli --root /Users/dakh/Git/_my/cod-doc-swarm doctor        # обязательно
./swarm-cli --root /Users/dakh/Git/_my/cod-doc-swarm go --goal "…"
```

Цель берётся из БД cod-doc, а не выдумывается: бэклог живёт в
`.cod-doc/state.db`, у задач есть `task_id`, описание и критерии
приёмки. Готовую задачу отдают планировщику целиком — идентификатором,
описанием и критериями, — чтобы `task_id` дошёл до сообщений коммитов:

```sh
cd /Users/dakh/Git/_my/cod-doc
GOAL=$(.venv/bin/cod-doc task show SYM-003 2>/dev/null || true)
```

Разбор блокировок — `swarm why`, вопросы петли — `swarm inbox`.

## 8. Закрытие задачи — в БД cod-doc, а не в стенде

Рой производит КОММИТЫ. Закон cod-doc (`CLAUDE.md`, `AGENTS.md`) требует
закрывать задачу записью в БД с sha коммита, а `.cod-doc/` в
`.gitignore` — то есть в стенде базы проекта нет вовсе, и агенты до неё
не дотягиваются. Это сознательно: автономная петля не пишет в источник
правды проекта.

Порядок после прогона — руками, в рабочем чекауте:

```sh
cd /Users/dakh/Git/_my/cod-doc
git log --oneline swarm/main ^main        # что рой сделал
git merge --no-ff swarm/main              # или cherry-pick нужного
# затем task_complete с sha коммита — через MCP-тул или CLI cod-doc
```

| Что | Значение |

| полный гейт (ruff + format + mypy + pytest) | 6 мин 59 с |
| тестов | 1388 passed |

задачу, которая просто медленно считалась, и стоит раунда.
