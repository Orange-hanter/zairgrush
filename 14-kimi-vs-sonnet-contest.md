# 14 — Состязание: Kimi 2.8 Code vs Claude Sonnet 5

Дата: 2026-09-18
Формат: слепое парное соревнование по 4 дисциплинам (кодинг, архитектура, стилистика, паттерны) с детерминированным судейством там, где возможно, и слепым human/LLM-judge там, где нет.

## 0. Контекст: что говорят открытые бенчмарки

Снимок на сентябрь 2026 (источники — живые лидерборды, цифры плавают):

| Бенчмарк | Что меряет | Sonnet 5 | Kimi (ближайший опубликованный) |
|---|---|---|---|
| SWE-bench Verified | фикс реальных GitHub-issues, прогон тестов репо | 85.2% ([Onyx, июль 2026](https://onyx.app/insights/best-llms-for-coding-2026)) | K2.6: 80.2%; K2.5: 76.8% ([arXiv 2602.02276](https://arxiv.org/pdf/2602.02276v1)) |
| SWE-bench Pro | 1865 contamination-resistant SE-задач (Scale AI) | — | Opus 4.6 лидирует с 47.1% ([Morph, сен 2026](https://www.morphllm.com/swe-bench-pro)) |
| LiveCodeBench v6 | свежие competitive-задачи, защита от контаминации | — | K2.5: 85.0% (выше Opus 4.5 = 82.2%) |
| Terminal-Bench 2.0 | агентная работа в реальном терминале | — | K2.6: 66.7% (лучший open-source) |
| BenchAlign coding (BenchLM) | взвешенный микс SWE-Pro + LCB | топ-5 — Claude Fable 5.1 / Fable 5 / Opus 5 | Kimi K3: 6 место, 67.7% ([BenchLM, 18.09.2026](https://benchlm.ai/coding)) |

Выводы из бенчмарков, которые определяют дизайн состязания:

1. **Sonnet 5 сильнее на SWE-bench-классе задач** (навигация по чужому коду, точечный фикс под тесты). Разрыв ~5 п.п. против Kimi K2.6 — это реальный, но не подавляющий гэп; у Kimi 2.8 он может закрыться.
2. **Kimi традиционно силён в LiveCodeBench** (новые алгоритмические задачи) и в терминальной агентности.
3. Публичные бенчмарки не меряют **архитектуру, стилистику и паттерны** — там нужен собственный протокол. Это и есть главная ценность нашего состязания.
4. HumanEval насыщен (>90% у всех фронтир-моделей) — в состязание не берём.

## 1. Регламент

**Участники:** Kimi 2.8 Code (kimi-code CLI) и Claude Sonnet 5 (API или claude-code CLI), оба в одинаковом агентном контуре: те же инструменты (bash/read/edit), тот же лимит токенов и ходов, одинаковый системный промпт-скелет.

**Принципы:**
- **Слепота:** судья не знает, чьё решение. Артефакты нормализуются (убираются self-references, случайные id в именах веток/коммитов).
- **Воспроизводимость:** каждая задача — git-репозиторий с зафиксированным SHA, задача выдаётся файлом `TASK.md`; решение — один патч/diff + лог сессии.
- **Бюджеты:** фиксированные лимиты на задачу (ходы/токены/время). Превышение = техническое поражение в задаче.
- **Без контаминации:** задачи либо свежие (написаны после cutoff обеих моделей), либо мутированные версии известных (см. §3).

**Счёт:** 4 дисциплины × N задач. Победа в дисциплине = 1 очко матча; ничья допустима. Итог — матчевый счёт + детальный расклад.

## 2. Дисциплина A — Кодинг (вес: 1 очко)

Детерминированное судейство: тесты решают. 6 задач по нарастающей сложности.

| # | Задача | Что проверяет | Судейство |
|---|---|---|---|
| A1 | Реализация LRU-кэша с TTL и stats (Python, ~150 строк) | корректность по спецификации | 40 скрытых юнит-тестов, включая граничные |
| A2 | Парсер подмножества cron-выражений + next-fire | точность edge-cases (29 февраля, DST не учитываем — явно в спеке) | property-based тесты (hypothesis) |
| A3 | Баг-фикс в реальном репо: берём 2 задачи формата SWE-bench из свежего rolling-бенча (SWE-Rebench, окно после июля 2026) | навигация по чужой кодовой базе | тесты репозитория (FAIL→PASS) |
| A4 | Мини-сервис: REST API очереди задач с приоритетами (FastAPI/Express — стек в спеке) | e2e-сборка работающего сервиса | контрактные тесты через HTTP |
| A5 | Рефакторинг под тест: «спагетти-модуль» 400 строк → разбить, сохранив поведение | рефакторинг без регрессий | существующие тесты зелёные + лимит цикломатической сложности |
| A6 | Миграция данных: скрипт переноса SQLite→JSONL с обратной совместимостью и rollback | аккуратность, идемпотентность | тесты + повторный прогон = no-op |

Очко дисциплины: доля пройденных задач; при равенстве — доля пройденных тестов внутри проваленных.

## 3. Дисциплина B — Архитектура (вес: 1 очко)

Судейство слепое: рубрика + панель (1 человек + LLM-judge из третьей лаборатории, не участник).

| # | Задача | Что проверяет |
|---|---|---|
| B1 | **Design-doc:** спроектировать систему «отложенные уведомления с дедупликацией» (10 RPS → 10k RPS). Требуется: компонентная схема, модель данных, failure modes, план масштабирования | полнота, осознание trade-offs, честность про ограничения |
| B2 | **Ре-архитектура:** дан легаси-монолит (~3k строк, генерируем специально): предложить декомпозицию и реализовать первый шаг strangler-фасада | связь плана и кода, обратная совместимость |
| B3 | **ADR-поединок:** обеим моделям одно архитектурное решение (напр. «event sourcing для биллинга»). Написать ADR: контекст, альтернативы (≥3), последствия, когда решение невалидно | качество альтернатив и «когда не применять» |
| B4 | **Ревью чужой архитектуры:** найти 5 подставленных архитектурных дефектов в заданной системе (god-service, distributed monolith, отсутствие idempotency, sync-цепочка, unbounded queue) | recall/precision найденных дефектов |

Рубрика B (каждая задача 0–10): корректность (4), полнота (2), trade-off awareness (2), ясность изложения (2). B4 — детерминированно: precision × recall по 5 дефектам.

## 4. Дисциплина C — Стилистика (вес: 1 очко)

Гибрид: линтеры детерминированно + слепое чтение человеком.

| # | Задача | Что проверяет |
|---|---|---|
| C1 | Написать модуль **в стиле существующего репо**: даём репозиторий с выраженной идиоматикой (напр. error-обёртки, логирование, naming), задача — новый модуль, неотличимый по стилю | соответствие house-style: линтер-конфиг репо + слепая пара «угадай автора» |
| C2 | Комментарии и докстринги: задокументировать недокументированный публичный API | точность (без выдумок!), краткость, отсутствие шума («этот метод возвращает результат») |
| C3 | Читаемость под ревью: одна и та же фича, оценивается diff как PR — размер, naming, структура коммита | слепая оценка «хочу ли я ревьюить это» + метрики (LOC диффа, cyclomatic, число ответственностей на функцию) |
| C4 | Обработка ошибок: дан happy-path код, добавить production-grade error handling | идиоматичность, отсутствие пустых catch, полезность сообщений |

Слепая процедура C1: судье дают 3 файла — 2 из репо, 1 от модели; задача угадать чужеродный. Если судья ошибается ≥ 2 раз из 3 раундов — стиль «нативный», полный балл.

## 5. Дисциплина D — Паттерны (вес: 1 очко)

| # | Задача | Что проверяет |
|---|---|---|
| D1 | **Применение:** реализовать под спецификацию 3 паттерна там, где они уместны (retry с backoff + circuit breaker; outbox; saga) | корректность реализации (тесты на failure-сценарии) |
| D2 | **Распознавание:** в заданном коде назвать использованные паттерны и антипаттерны (12 подставленных, включая ложные друзья — «похоже на singleton, но не он») | precision/recall, качество объяснения |
| D3 | **Отказ от паттерна:** задача, где очевидное паттерн-решение вредно (напр. «не нужен DI-контейнер на 3 зависимости»). Ожидается простое решение + обоснование отказа | YAGNI-дисциплина: штраф за over-engineering |
| D4 | **Трансформация:** переписать callback-ад на async/await (или Rx на корутины) с сохранением семантики отмены и ошибок | эквивалентность поведения под тестами отмены/гонок |

D3 — ключевая дифференцирующая задача: метрика = (тесты пройдены) − (штраф за лишние абстракции по чек-листу: лишний интерфейс, лишняя фабрика, config ради config).

## 6. Анти-контаминация и честность

- Задачи A1, A2, A6, B1, C*, D* — **авторские, новые**, хранятся в приватном репо до прогона. Не публиковать до конца матча.
- A3 — только из SWE-Rebench-окна позднее обоих cutoff'ов; проверить, что issue не в тренировочных данных (поиск точной формулировки).
- Каждой модели — **свежий инстанс**, без памяти между задачами; температура и параметры фиксируются в логе.
- Сырые логи сессий сохраняются (`experiments/contest/logs/`) — аудит доступен обеим сторонам.

## 7. План проведения (5 дней)

| День | Этап | Артефакт |
|---|---|---|
| 1 | Финализация задач, сборка репозиториев-контейнеров, прогон sanity (задачи решаемы человеком/эталоном) | `experiments/contest/tasks/` + goldset |
| 2 | Прогон дисциплин A и D (детерминированное судейство — сразу счёт) | результаты + логи |
| 3 | Прогон B и C, нормализация артефактов для слепого судейства | blind-пакеты |
| 4 | Судейство B и C (рубрики, протокол заседания панели) | заполненные рубрики |
| 5 | Подсчёт, разбор спорных задач, отчёт | `experiments/contest/REPORT.md` |

Инфраструктура: раннер задач = `experiments/driver/` (уже есть драйвер контуров), судейский пакет = рубрики в `experiments/goldset/`-стиле. Бюджет на задачу по умолчанию: 30 ходов / 200k токенов / 45 минут (подтвердить после sanity-прогона).

## 8. Критерии итога

- Матчевый счёт: 4 очка (по одному на дисциплину).
- Дополнительно фиксируем (не в счёт, но в отчёт): стоимость токенов на задачу, время, число ходов, % сессий без технических сбоев.
- Ничья по очкам → тай-брейк: суммарный балл рубрик B+C, затем стоимость.

## 9. Открытые вопросы (решить до дня 1)

1. Идентичен ли агентный контур? Sonnet 5 в claude-code против Kimi в kimi-code — разные инструменты искажают сравнение. Вариант «честнее»: обе модели через OpenRouter в одном самописном мини-харнесе.
2. Кто в панели судей для B/C? Нужен ≥1 человек, не знающий расклад.
3. LLM-judge для B/C: какая модель (не участник — напр. GPT-5.5), с рубрикой и few-shot калибровкой.
4. Публикуем ли задачи и логи после матча (репутационный риск/польза).
