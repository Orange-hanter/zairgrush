# tools/swarm — реализация петли

CLI `swarm` и оркестратор мультиагентной петли разработки: планировщик
раскладывает цель на задачи, исполнитель пишет дифф, ревьюер судит его
по критериям приёмки, оркестратор гоняет гейт и коммитит после approve.
Дизайн — `05-agent-swarm.md` (§-ссылки ниже — на него); руководство
оператора — `08-operators-guide.md`.

Проверка — одна команда: `./check.sh` (линт → типы → тесты). Инструменты
ставятся в `.venv`: `uv venv .venv && uv pip install --python .venv ruff mypy pytest`.

## Выбор движка исполнителя

Кем именно исполняется задача, решает `swarm/engines.py` (§3.2, E10, E13).

- Ключ `executor_engine` в `swarm.toml` принимает ровно четыре значения:
  `kimi`, `claude`, `ollama`, `zcode`. Умолчание — `kimi`. Незнакомое
  значение не откатывается к умолчанию, а отказывает: молчаливо выбранное
  умолчание — тот отказ, что дал «ноль вызовов эмбеддера за весь пилот».
- Альтернативный путь — префикс движка в `executor_model` по первому
  двоеточию: `"ollama:kimi-k2.7-code"` ведёт заливку на дешёвую модель,
  `"zcode:glm-5.3-flash"` — на zcode. Префикс СТАРШЕ ключа
  `executor_engine`: так план-дифф пришпиливает отдельную задачу к другому
  движку, не трогая настройку прогона.
- Урок E13: модель пришпиливается ЯВНО (`executor_model` в конфиге или в
  задаче плана). Непришпиленный исполнитель наследует машинный
  `default_model` из настроек CLI — тот сменился с `k3` на `k3-256k`, и
  плечо замера незаметно перестало быть плечом. Исключение — zcode: CLI
  не принимает `--model`, хвост после префикса живёт только в метрике.
- Смена движка — операция конфига, а не кода: для замера плечи отличаются
  ровно этими строками в `swarm.toml` (см. `experiments/stand-e13-a/`).

Ревьюер, планировщик и документатор ходят через `claude` и от выбора
движка исполнителя не зависят: независимость судьи — несущая опора
разделения ролей (§3.2).
