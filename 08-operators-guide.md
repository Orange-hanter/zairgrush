# Руководство оператора

Это инструкция для человека, который ведёт разработку через петлю. Она не
объясняет устройство системы — для этого есть [05-agent-swarm.md](05-agent-swarm.md).
Здесь только то, что нужно делать руками, в порядке, в котором это делается.

Главное, что стоит понять до начала: **вы не наблюдатель, а участник
контура**. Петля сама не принимает решений о замысле — она их вам
приносит. Работа оператора состоит из трёх действий: поставить задачу,
ответить на вопросы, просмотреть коммит. Всё остальное механическое.

## 1. Подготовка

### Отдельный клон — не перестраховка

Работайте в отдельном клоне или `git worktree`, а не в основном рабочем
дереве:

```sh
git clone <репозиторий> ~/work/zeus-swarm
cd ~/work/zeus-swarm
```

Причина конкретная. Петля откатывает файлы и делает `git add -A`.
Реализованы preflight (отказ на грязном дереве) и точечный откат, который
не трогает то, что лежало в дереве до старта задачи, — но изоляция
процесса не сделана: агент технически может прочитать `.env` или
выполнить команду вне рабочего дерева. В отдельном клоне терять нечего, а
в основном дереве — есть что.

### Проверка окружения

```sh
swarm --root . doctor
```

Он проверяет наличие обоих CLI, версию ctags (Exuberant отвергается),
чистоту дерева и видимость состояния. Половина дефектов программы
экспериментов была не в петле, а в среде — не та реализация ctags,
отсутствующий инструмент, урезанный `PATH`. Тридцать секунд здесь
экономят час диагностики потом.

### Конфигурация прогона

`swarm.toml` в корне целевого репозитория:

```toml
# Гейт — то, что делает работу принятой. Включайте сюда ВСЁ, что упадёт
# в CI: тесты, формат, линт. Требование, которое исполнитель не может
# проверить сам, превращает ревью в бесконечный круг — на приёмке одна
# задача не сходилась четыре прогона из-за `ruff format`, которого не
# было в гейте.
gate_command = ["sh", "-c", "cargo test && cargo fmt --check && cargo clippy -- -D warnings"]

# Пути, которые считаются чужими тестами и защищены от правки
protected_paths = ["tests/*", "tests/**", "*.toml"]

confirmations = 2        # подтверждений перед закрытием задачи
max_iterations = 3       # раундов исправлений (подтверждение их не тратит)
gate_timeout = 3600      # секунд; холодная сборка Rust в 900 не влезает
map_budget = 25          # символов в карте репозитория
review_budget_usd = 3.0  # потолок на ОДИН вызов ревьюера
total_budget_usd = 50.0  # потолок на ВЕСЬ прогон: петля остановится сама
verification = "milestone"  # проверки исполнением: never | milestone | always
live_board = true        # перестраивать .swarm/board.html после каждого раунда
quota_backoff_s = [60, 120, 240]  # паузы при отказе провайдера по квоте
plan_timeout = 900       # секунд на один вызов планировщика
```

Опечатка в имени ключа не проходит молча: незнакомый ключ петля называет
в предупреждении при старте — иначе вы были бы уверены, что настройка
действует, а работало умолчание.

**Про деньги отдельно.** `review_budget_usd` — потолок на один вызов
ревьюера; на Rust-диффах $1.5 не хватало, потому что повторный проход
(после проверок исполнением) дороже первого. `total_budget_usd` — потолок
на весь прогон: петля считает траты по факту метрик и **останавливается
сама** — проверка стоит перед каждой итерацией, так что и одна
затянувшаяся задача не пробьёт потолок на много раундов. Если стоп
пришёлся посреди задачи, она не виновата: работа уходит в stash, задача
возвращается в очередь, и после поднятия бюджета прогон продолжается тем
же `go`. Обе цифры задаёте вы; без `total_budget_usd` ограничения нет
вовсе. Известное слепое пятно: Kimi не сообщает стоимость своих вызовов,
поэтому траты исполнителя в счёт не входят — бюджет ограничивает вызовы
claude (ревью и планирование).

Перед первым прогоном прогрейте сборку (`cargo build`), иначе первая же
компиляция может упереться в `gate_timeout`.

**Что класть в гейт, кроме тестов.** Линт и проверку типов — не для
красоты. На самом оркестраторе при 538 зелёных тестах строгий `ruff` и
`mypy --strict` дали около полусотни содержательных находок, которых
тесты не находили: молча проглоченный битый конфиг, необработанный
`None`, адрес из переменной окружения без проверки схемы (§6.6). Порядок
внутри гейта — дешёвое раньше дорогого: линт, типы, тесты. Собственный
гейт роя устроен так же и живёт одной командой — `tools/swarm/check.sh`.

**Baseline должен быть зелёным.** Петля не запускает задачу на красном
гейте (§5.0) — и правильно делает: иначе исполнитель чинит чужую поломку
вместо своей задачи. Если в репозитории есть падающий тест, который вы
чинить не собираетесь, исключите его в `gate_command` явно и напишите в
комментарии почему.

## 2. Постановка задач

Задачи живут в `.swarm/tasks.json`. Их можно писать руками или получить
от планировщика.

### Планировщиком

```sh
swarm --root . plan --goal "Закрыть пробелы валидации в zeus-library" --dry-run
swarm --root . plan --goal "Закрыть пробелы валидации в zeus-library"
```

`--dry-run` показывает предложенный дифф, не применяя его. Планировщик
видит состояние репозитория и текущую очередь, а его выход механически
валидируется: уникальность id, обязательность `paths`/`acceptance`,
разрешимость `deps`, отсутствие циклов, отсутствие конфликтующих операций.
Невалидный дифф — одна повторная попытка, потом отказ.

### Руками

```json
{
  "id": "v1we",
  "title": "wait_exponential: валидация аргументов",
  "type": "feature-tests",
  "status": "pending",
  "deps": [],
  "paths": ["tenacity/wait.py", "tests/test_swarm_validation.py"],
  "test_module": "tests/test_swarm_validation.py",
  "gate": "full",
  "spec": "wait_exponential молча принимает бессмысленные аргументы: min=10, max=5 создаётся без ошибки. Добавить проверку в __init__: min не больше max, multiplier положительный. При нарушении — ValueError с внятным сообщением, называющим параметр и значение.",
  "acceptance": [
    "весь существующий сьют проходит без изменений",
    "wait_exponential(min=10, max=5) возбуждает ValueError",
    "сообщения единообразны между стратегиями"
  ]
}
```

Поля, которые определяют поведение петли:

| поле | что делает |
| --- | --- |
| `type` | `feature` — правит код, тесты трогать нельзя; `feature-tests` — пишет свои тесты сам, чужие не трогает; `test-task` — правит только тесты; `idea` — заметка на будущее |
| `paths` | границы задачи. Проверяются механически по факту изменений; выход за них откатывается |
| `acceptance` | по ним судит ревьюер. Пишите проверяемые утверждения, а не пожелания |
| `deps` | порядок. Задача не берётся, пока зависимости не закрыты |
| `milestone_close` | включает проверки исполнением на этой задаче (при `verification = "milestone"`) |

### Что заходит хорошо, а что плохо

**Хорошо:** правка существующих файлов на 10–50 строк; один связный
результат; явные `paths` на конкретные файлы; критерии приёмки, которые
можно проверить командой.

**Плохо:** «отрефактори модуль» без описания результата; задачи, где
`acceptance` — это «код стал чище»; несколько несвязанных изменений в
одной задаче. Такие задачи выжигают лимит итераций, и диагност скажет
«слишком крупная, расщепить» — он будет прав.

**Осторожно:** создание новых файлов и каталогов. Механически это теперь
защищено (новый файл виден и ревьюеру, и проверке границ), но на живом
прогоне ещё не проверялось. Первые такие задачи стоит смотреть глазами
внимательнее обычного.

### Независимый эталон: пишите, чем сверять ЗАПРЕЩЕНО

Если задача требует сверить поведение с независимо посчитанным
результатом, критерия «сверять с независимым эталоном» **недостаточно**.
Для человека фраза однозначна, для исполнителя — нет: он ищет
кратчайший путь к зелёному тесту и берёт то, что проверяемый код уже
произвёл.

На пилоте это случилось дважды подряд с одним и тем же тестом. Сначала
эталон повторил форматную строку `location`, которую строит правило, —
ошибка форматирования не поймалась бы никогда. После исправления эталон
стал сверять по ключу подавления, который строит то же правило, — и
снова проверял реализацию против самой себя.

Поэтому перечисляйте запрещённые источники поимённо:

```
"сверка идёт по паре (SymbolId, Terminal.name), полученной обходом модели",
"в основу сравнения ЗАПРЕЩЕНО класть поля, которые вычисляет само правило:
 location, suppression_key и их производные (мультимножества, хеши)"
```

Правило продублировано в промпте планировщика, так что автоматически
составленные задачи его тоже несут.

## 3. Рабочий цикл

### От А до Я одной командой

```sh
swarm --root . go --goal "Закрыть пробелы валидации в zeus-library"
```

`go` — это весь цикл: рой **сам** декомпозирует цель в задачи (планировщик
внутри петли, а не человек снаружи), сам их исполняет по очереди и
останавливается только на том, что действительно требует вас: вопрос о
замысле, исчерпанный бюджет, авария. В конце печатает итог, стоимость и
путь к доске.

Повторный `go` без `--goal` продолжает незаконченную очередь — так
возвращаются после ответов на вопросы:

```sh
swarm --root . answer q003 "решение"
swarm --root . go                       # продолжает с того же места
```

Планирование пропускается, если в очереди есть незакрытые задачи. Если
при этом передать `--goal`, отличную от сохранённой, `go` откажется (код
2) и назовёт обе цели: раньше он молча доигрывал старый план под старой
вывеской, и доска показывала не ту цель. Продолжить старую очередь —
`go` без `--goal`; новая цель — сперва `swarm plan --goal "..."`.

Код возврата `run`/`go` — контракт для обёрток (полная таблица — в
`swarm --help`): `0` — все взятые задачи закрыты; `3` — нет готовых
задач; `4` — пауза по квоте провайдера; `11` — есть blocked/ask_user,
нужны вы; `12` — остановка по бюджету; `13` — исполнитель недоступен;
`2` — ошибка вызова. `swarm go && deploy` больше не «сработает» на
прогоне, вставшем по бюджету.

### Наблюдение

```sh
swarm --root . board --open    # доска: задачи, фазы, стоимость, вопросы
```

Одна страница, на которой видно всё: что сделано и чем закончилось,
сколько стоила каждая фаза, что вошло в код, где вас ждут (с готовой
командой ответа) и какие решения вы уже приняли. Держите её открытой в
соседней вкладке во время прогона: петля переписывает страницу после
каждого раунда, так что F5 показывает свежее состояние. Внизу страницы —
время последней сборки; если оно не движется, значит не движется и
прогон. Отключить перестроение: `live_board = false` в `swarm.toml`.

Остановку прогона доска показывает сразу, без раскопок: блок «События
прогона» (исчерпанный бюджет, сорванное планирование) и блок «Шаги без
исхода — прогон падал» (интент коммита без записи о завершении, с
готовой командой `resume`) стоят над списком задач, а не в свёрнутой
хронике.

### Куда смотреть, когда прогон встал

```sh
swarm --root . why            # задача, которая первой требует внимания
swarm --root . why v2wf       # разбор конкретной задачи
```

`why` собирает в один ответ то, что раньше приходилось складывать из
пяти мест: статус и причину блокировки, собственный диагноз петли,
траекторию раундов с прочтением («находки убывают» / «стоит на месте —
это топтание»), последний вердикт ревьюера с находками, открытый вопрос,
метку stash с сохранённой работой, пути к сырым логам — и готовые
команды, которыми это разбирается. Это первое, что стоит запускать: не
`status`, а `why`.

`status` тоже заканчивается строкой «дальше» с одной конкретной командой
под текущее состояние очереди.

### Осторожный режим

```sh
swarm --root . status          # что в очереди, сколько потрачено
swarm --root . run --limit 1   # одна задача за прогон
```

Имеет смысл, пока доверие к постановке не сложилось, и на классах задач,
которые ещё не проверены живым прогоном (создание модулей).

Прогон заканчивается одним из исходов:

- **done** — задача закрыта и закоммичена. Смотрите `git log -p`.
- **ask_user** — есть находка о замысле, петля спрашивает вас.
- **blocked** — спор исполнителя, нарушение границ, исчерпание раундов,
  авария или нарушение доверия.

Во всех неудачных случаях работа не теряется: она уходит в `git stash` с
меткой, а задача получает вопрос в инбоксе.

### Разбор вопросов

```sh
swarm --root . inbox
swarm --root . answer q003 "текст решения"
swarm --root . answer q003 "текст решения" --add-path src/utils.rs
```

Отвечайте по существу замысла, а не по механике: механические находки
исполнитель чинит сам, вам приносят только то, что требует решения. Ответы
**накапливаются** — второй не затирает первый, и все они видны и
исполнителю, и ревьюеру в последующих раундах.

`--add-path` нужен, когда ваше решение требует тронуть файл вне границ
задачи. Без него исполнитель упрётся в проверку границ и будет откатан —
это уже случалось на приёмке: указание «вынеси в `_utils.py`» было
невыполнимо, потому что `_utils.py` не было в `paths`.

### Повторяющиеся замечания

Если ревьюер раз за разом требует одного и того же, а вы это решение уже
отклонили, — заведите политику прогона:

```sh
swarm --root . policy add "Release notes вне scope этого прогона" --match "release note" --match "reno"
swarm --root . policy list
```

Политика фильтрует находки **на стороне оркестратора**, а не затыкает
ревьюера: он продолжает сообщать всё, подавленное видно в `policy list` и
в отчёте. `blocker` не подавляется никогда — политика снимает требования к
оформлению, но не к корректности. Политика умирает вместе с целью прогона.

### Застрявшая задача

```sh
swarm --root . retry v2wf --note "указание, что делать иначе"
```

`retry` принимает задачи в `blocked` и в `in_progress` (вторая — когда
прогон умер на сбое).

## 4. Когда что-то идёт не так

**Первое правило: подозревайте обвязку, а не модель.** За всю программу
найдено 24 дефекта — все в оркестраторе, ни одного нарушения контрактов
моделями. Трижды подряд автоматический диагноз говорил «задача слишком
крупная», а виноваты были гейт без линтера, механика подтверждения и
парсер отчёта.

Порядок диагностики:

```sh
swarm --root . why v2wf               # почему встала и что нажать дальше
swarm --root . report --task v2wf     # хроника задачи связным текстом
swarm --root . report --task v2wf --json   # то же сырьём, без обрезки
cat .swarm/metrics.jsonl              # фазы, длительности, стоимость
ls .swarm/log/                        # сырые ответы агентов по итерациям
```

`report` печатает журнал фразами и группирует записи по задачам; события
прогона (бюджет, план, preflight) идут отдельным блоком «прогон в целом»
— они ничьи, и приклеенные к задаче объясняли бы остановку очереди не тем.
Ни одно поле записи не теряется: то, что не вошло во фразу, дописывается
хвостом `ключ=значение`. Если нужен точный первоисточник — `--json` даёт
те же строки без обрезки.

В `.swarm/log/` лежат `<task>-i<N>-executor.jsonl` (поток исполнителя),
`<task>-i<N>-a<M>-review.json` (конверт ответа ревьюера; фаза `v` —
повторный проход после проверок исполнением) и рядом
`<task>-i<N>-a<M>-review-stream.jsonl` — полный поток ревьюера. Если
поведение непонятно — читайте их раньше, чем правите постановку.

Типичные картины:

| симптом | где смотреть |
| --- | --- |
| задача не сходится за лимит | вердикты ревьюера: он требует чего-то, что исполнитель не может проверить? добавьте это в гейт |
| `no_report` подряд | поток исполнителя: он отвечает, но не по контракту? |
| «нарушение доверия» | исполнитель тронул историю или `.swarm/`; смотрите `integrity_violation` в журнале |
| авария прогона | `task_crashed` в журнале, работа в stash, задача в `blocked` |
| пауза по квоте | `quota_wait`/`quota_pause` в журнале (ревью) или reason="quota" в plan-metrics.jsonl (планирование); задача в `pending`, работа в stash — переждите и повторите `go` |
| планировщик молчит дольше plan_timeout | вызов остановлен, причина `timeout` в plan-metrics.jsonl; один повтор делается сам, дальше — поднять `plan_timeout` или сузить цель |

**Коды возврата.** `0` — все взятые задачи закрыты; `2` — отказ,
требующий вашего решения (preflight, эскалация resume, противоречивое
состояние, `--goal` не совпала с сохранённой); `3` — нет задач, готовых
к запуску; `4` — пауза по квоте провайдера: петля подождала по
нарастающей (`quota_backoff_s`), квота не отпустила, задача возвращена в
очередь — повторите `go`, когда лимит сбросится; `11` — есть исходы
blocked/ask_user, разбирайте инбокс; `12` — остановка по бюджету
прогона; `13` — исполнитель недоступен (мгновенные аварии процесса —
смотрите stderr в журнале, `executor_failed`).

**`swarm resume` после падения.** Незавершённый шаг коммита resume
разбирает сам: в intent-записи лежит `head` до действия, и по истории
видно, состоялся ли коммит. Коммита не было — задача возвращается в
очередь; коммит оркестратора найден — задача закрывается им. Требовать
`--force` resume продолжает только там, где механически решить нельзя:
интент старого формата без `head` или чужой коммит поверх.
`resume --dry-run` показывает, ЧТО будет сделано, не трогая ни журнал,
ни очередь.

**Восстановление работы из stash.** Метка вида `swarm:v3st-max-iterations`
видна в `git stash list` и в поле `stash` задачи. Петля сама её не
применяет — это ваше решение.

## 5. Что смотреть глазами

Инструмент проверяет механику: тесты, границы, формат контрактов,
неизменность истории. Он не проверяет замысел. Ваш просмотр —
единственное место, где ловится «сделано правильно, но не то».

Минимум на каждый коммит: `git log -p -1`. На что смотреть в первую
очередь — на соответствие `acceptance` и на то, не решена ли задача
формально (проверка добавлена так, что тест проходит, а смысла нет).

Раз в несколько задач полезно:

```sh
swarm --root . map --budget 40      # карта символов: не расползлась ли структура
swarm --root . impact <symbol>      # кто зовёт символ перед его правкой
```

## 6. Границы применимости

Что система делает надёжно: правки существующего кода по чётким критериям,
с полным сьютом в гейте, на проектах масштаба нескольких тысяч файлов.

Что не проверено: создание модулей на живом прогоне; проекты в 10–100 раз
крупнее приёмочного стенда; языки без точного индекса (индекс символов
сделан для Python, для Rust работает tree-sitter приблизительно);
параллельные пары на разных worktree.

Что не сделано: изоляция исполнителя. Пост-проверка ловит изменение
истории, правку состояния петли и незавершённые rebase/merge, но не
помешает агенту прочитать `.env`. Отсюда требование отдельного клона в
§1 — оно не формальность.
