# Руководство оператора

Это инструкция для человека, который ведёт разработку через петлю. Она не
объясняет устройство системы — для этого есть [05-agent-swarm.md](05-agent-swarm.md).
Здесь только то, что нужно делать руками, в порядке, в котором это делается.

Главное, что стоит понять до начала: **вы не наблюдатель, а участник
контура**. Петля сама не принимает решений о замысле — она их вам
приносит. Работа оператора состоит из трёх действий: поставить задачу,
ответить на вопросы, просмотреть коммит. Всё остальное механическое.

## 1. Подготовка

### Отдельный клон — не перестраховка

Работайте в отдельном клоне или `git worktree`, а не в основном рабочем
дереве:

```sh
git clone <репозиторий> ~/work/zeus-swarm
cd ~/work/zeus-swarm
```

Причина конкретная. Петля откатывает файлы и делает `git add -A`.
Реализованы preflight (отказ на грязном дереве) и точечный откат, который
не трогает то, что лежало в дереве до старта задачи, — но изоляция
процесса не сделана: агент технически может прочитать `.env` или
выполнить команду вне рабочего дерева.

One class of files is safe by construction: `swarm.toml` and `.swarm/`
belong to the loop, not to tasks. The scope guard never judges them, the
loop never reverts, stashes, or commits them, and the reviewer does not
see their diff — so an operator edit to the run config made mid-run
stays in the tree untouched (it still takes effect only on the next
process start, and preflight will name it as dirt). Any other
uncommitted operator file is likewise spared for the whole run: the loop
snapshots the dirty list at start (`run_dirt` in the journal) and never
attributes those files to the executor. В отдельном клоне терять нечего, а
в основном дереве — есть что.

### Проверка окружения

```sh
swarm --root . doctor
```

Он проверяет наличие обоих CLI, версию ctags (Exuberant отвергается),
чистоту дерева и видимость состояния. Половина дефектов программы
экспериментов была не в петле, а в среде — не та реализация ctags,
отсутствующий инструмент, урезанный `PATH`. Тридцать секунд здесь
экономят час диагностики потом.

Одно ограничение среды доктор теперь проверяет машиной: стенд не должен
лежать внутри каталога `.claude/`. Файлы там Claude Code считает
чувствительными и править отказывается, поэтому исполнитель возвращает
`dispute` вместо работы — и выглядит это спором о постановке задачи, а не
ловушкой среды. Прозой это правило стояло в руководстве и раньше; строку
`[ПРОБЛ] стенд` доктор печатает с 2026-08-26, после того как первая
попытка развернуть стенд на cod-doc легла ровно сюда (`EnterWorktree` в
Claude Code кладёт worktree именно в `.claude/worktrees/`).

Про tree-sitter доктор говорит послойно: brew-пакет `tree-sitter` — это
только C-библиотека, а слою индексации (`map --tree-sitter`, полезен для
Rust) нужны python-биндинги и обе грамматики. Если стоит лишь часть,
доктор называет установленный слой и печатает точную команду
(`pip install tree-sitter tree-sitter-python tree-sitter-rust`) — раньше
он отвечал «не установлен» человеку, у которого `brew list` показывал
tree-sitter, и спор шёл о двух разных вещах.

### Кем исполнять: движок исполнителя

До 2026-08-22 ответ был один — `kimi`, и в коде он был прибит намертво.
Ревьюер, планировщик и документатор ходят через `claude`, и только у
исполнителя не было запасного пути: кончилась подписка — встал рой.
Теперь движок называется в `swarm.toml`:

```toml
executor_engine = "claude"   # kimi (умолчание) | claude | ollama | zcode
executor_model  = "sonnet"
```
(про `zcode` — отдельный блок ниже; здесь речь о движке `claude`)

Умолчание кода не менялось — `kimi`. Стенд, ничего не настроивший,
работает ровно как вчера; это не осторожность, а условие сравнимости
замеров (E8, E10). Этот репозиторий на `zcode` сам не переключается.

Что меняется на движке `claude`, кроме имени процесса:

- **Исполнитель наконец стоит денег на бумаге.** Поток kimi не содержит
  ни цены, ни токенов; конверт claude содержит. Цена идёт в метрику
  раунда и в `total_budget_usd` (см. «Про деньги отдельно»).
- **Запрет на запись в git стал механикой.** Промпт всегда говорил
  исполнителю «git для тебя только для чтения», но проверял это лишь
  страж границ постфактум. Здесь `git commit|push|reset|rebase|merge|
  checkout|stash|config` отклоняются ДО выполнения, а попытка попадает в
  журнал строкой `executor_denied` — вы её увидите, а не догадаетесь.
  Чтение (`git diff`, `git log`, `git status`) остаётся разрешённым.
- **Квота лечится паузой, а не блокировкой задачи.** У kimi отказ по
  квоте приходил мгновенной смертью процесса; claude называет её словами,
  и исполнитель попадает в ту же механику ожидания, что ревьюер.

**Цена выбора, о которой лучше знать заранее.** Разделение ролей
опиралось в том числе на независимость судьи: дифф пишет одна модель,
судит другая. Исполнитель и ревьюер на одном семействе эту опору
убирают. Петля скажет об этом сама на старте прогона, если модель
исполнителя и `review_model` совпали; развести их можно тем же, чем
разводятся раунды подтверждения — `confirm_model`, `confirm_effort`,
`confirm_lens`. Насколько это влияет на число находок — не измерено
(эксперимент E15; в 06-доке E13 — это сравнение движков исполнителя,
там вопрос семейства жил как caveat).

**Одно ограничение среды, найденное пробой.** Стенд не должен лежать
внутри каталога `.claude/`: файлы там Claude Code считает
чувствительными и отказывается править, и исполнитель честно вернёт
`dispute` вместо работы.

`swarm doctor` печатает выбранный движок первой строкой и проверяет
именно его; отсутствие невыбранного CLI — не поломка, а другая
конфигурация стенда.

**Движок `zcode` (клиент Z.AI, замерено 0.16.5).** Третий CLI
исполнителя, не ревьюер и не планировщик. Включается ключом, умолчание
не трогает:

```toml
executor_engine = "zcode"
executor_model  = "glm-5.3"   # пример имени: пишется в метрику, на argv не
                              # кладётся; реальная модель — в ~/.zcode/cli/config.json
```

Как зовётся процесс. `which zcode` — если пусто, петля берёт бандл
приложения: `node /Applications/ZCode.app/Contents/Resources/glm/zcode.cjs`
(путь macOS; на Linux/Windows фолбэка на бандл нет — там нужен
официальный `zcode` CLI в PATH, см. сайт Z.AI).
Не ставьте npm-пакет `zcode` / `zcode-app-cli` и не гоняйте GLM через
Claude Code с `ANTHROPIC_BASE_URL` — это другие продукты.

Флаги headless-вызова всегда явные, чтобы TUI-умолчания не протекли:
`--prompt` (stdin драйвер и так глушит), `--json` (один объект, не
NDJSON), `--mode yolo`, `--allowed-tools` /
`--disallowed-tools` с git-deny
(у zcode список шире, чем у claude: `--mode yolo` делает deny-list
единственным барьером, поэтому туда добавлены `git revert`, `cherry-pick`,
`clean -f`, `rm`, `branch`, `tag`; записи вида `Bash(git commit:*)` —
**не** справочный пример `Bash(git *)`, тот закрыл бы даже `git diff`;
точные списки — константы `CLAUDE_DENIED_TOOLS` / `ZCODE_DENIED_TOOLS` в
`swarm/engines.py`), `--cwd` рабочего дерева, `--surface terminal`.
`--browser-use` и `--verbose` не передаются: второе пачкает stdout.

Модель живёт в `~/.zcode/cli/config.json`, не во флаге CLI: `--model`
у 0.16 нет. `executor_model` выбирает движок префиксом `zcode:…`
(например `executor_model = "zcode:glm-5.3"` в задаче плана — префикс
старше ключа `executor_engine`; в примере выше префикс не нужен, движок
уже задан ключом) и пишется в метрику; доктор при выбранном `zcode` и
заданной модели печатает её имя в строке статуса движка. `zcode login`
через OAuth на этой машине ненадёжен — рабочий путь: ключ Coding Plan
или вход через GUI приложения.

`--json` может молчать до конца вызова. Драйвер считает процесс живым,
пока в stdout **или** stderr что-то пишется чаще, чем раз в
`silence_timeout`; умолчание 600 секунд. Тишина на обоих потоках дольше
таймаута = зависший процесс. Длинный прогон — поднимите ключ, иначе
петля остановит живой процесс как зависший.

Цена из конверта не приходит: токены (`inputTokens` /
`outputTokens` / `cacheReadTokens`) в метрику идут, `cost_usd` петля
не выдумывает. В `total_budget_usd` исполнитель на `zcode` не
складывается, как на `kimi`. Отказ по квоте ZCode в механику пауз не
заведён, пока нет замерённого текста отказа — то есть квотный отказ
zcode придёт как мгновенная смерть процесса (симптом: раунд падает
сразу, в журнале нет строки паузы), а не как ожидание сброса.

### Конфигурация прогона

`swarm.toml` в корне целевого репозитория:

```toml
# Гейт — то, что делает работу принятой. Включайте сюда ВСЁ, что упадёт
# в CI: тесты, формат, линт. Требование, которое исполнитель не может
# проверить сам, превращает ревью в бесконечный круг — на приёмке одна
# задача не сходилась четыре прогона из-за `ruff format`, которого не
# было в гейте.
gate_command = ["sh", "-c", "cargo test && cargo fmt --check && cargo clippy -- -D warnings"]

# Пути, которые считаются чужими тестами и защищены от правки
protected_paths = ["tests/*", "tests/**", "*.toml"]

confirmations = 2        # подтверждений перед закрытием задачи
max_iterations = 3       # раундов исправлений (подтверждение их не тратит;
                         # раунд, сорвавшийся до суждения о работе, — тоже)
max_futile_rounds = 4    # потолок сорвавшихся раундов (умолчание тянется
                         # за max_iterations): авария исполнителя, откат
                         # по границам, разъехавшиеся сигнатуры
gate_timeout = 3600      # секунд; холодная сборка Rust в 900 не влезает
map_budget = 25          # символов в карте репозитория
review_budget_usd = 3.0  # потолок на ОДИН вызов ревьюера
total_budget_usd = 50.0  # потолок на ВЕСЬ прогон: петля остановится сама
verification = "milestone"  # проверки исполнением: never | milestone | always
live_board = false       # true — HTTP на board_port, автооткрытие в браузере
board_port = 7433        # порт живой доски; занят — сервер возьмёт свободный
quota_backoff_s = [60, 120, 240]  # паузы при отказе провайдера по квоте
quota_resume = "auto"    # квота кончилась — дождаться сброса и продолжить
                         # самому (дефолт off: пауза и exit-код 4);
                         # потолки: quota_resume_max = 3 попытки на прогон,
                         # quota_resume_max_wait_s = 21600 (дальше — человеку)
plan_timeout = 900       # секунд на один вызов планировщика

# КЕМ исполнять. Умолчание — kimi (как было всегда); claude, ollama и
# zcode включаются здесь. executor_model — модель этого движка; префикс
# ("claude:sonnet", "zcode:glm-5.3") старше ключа и нужен, когда движок
# задаётся на ОТДЕЛЬНУЮ задачу в плане, а не на весь прогон.
# У zcode хвост модели в метрике есть, на argv его нет (CLI 0.16).
executor_engine = "claude"     # kimi | claude | ollama | zcode
executor_model = "sonnet"
executor_effort = "medium"     # только для claude; не задан — сессионный
executor_budget_usd = 2.0      # только для claude; потолок на ОДИН вызов
silence_timeout = 600          # секунд тишины на ОБОИХ потоках (stdout+stderr)
                               # одного вызова ЛЮБОЙ CLI-роли — исполнителя,
                               # ревьюера, планировщика (имя историческое:
                               # ключ появился для исполнителя, действует на
                               # всех); zcode --json молчит до финала —
                               # не режьте
```

**Режим траты денег: `spending`.** С 2026-08-24 умолчание —
`money_bin` («денежный чан»): у петли НЕТ неявных потолков на вызов
роли. Прежнее поведение возвращается одним словом.

```toml
spending = "money_bin"   # money_bin (умолчание) | capped
```

Что именно меняется. Потолков в петле два вида, и путать их дорого.
ЯВНЫЙ — число, которое вы написали в конфиге; он действует ВСЕГДА, в
любом режиме, потому что настройка, молча перестающая работать, — худший
из отказов этого инструмента. НЕЯВНЫЙ — умолчание кода, которого никто
не просил; такой был один и висел на самой дорогой роли: ревьюер звался
с `--max-budget-usd 1.0`, даже если о деньгах в конфиге не было ни
слова. Он и срабатывал — «ревьюер обрублен по бюджету» есть в списке
штатных диагнозов выше.

- `money_bin`: неявных потолков нет. `total_budget_usd`,
  `review_budget_usd`, `executor_budget_usd`, `plan_budget_usd` — если
  вы их задали, они в силе; если нет, потолка нет.
- `capped`: как было — у ревьюера умолчание $1.
- Явный `0` читается как «снять потолок», а не как «обрубить
  немедленно»: иначе ноль был бы ловушкой.
- Потолок ПРОГОНА (`total_budget_usd`) неявным не бывает ни в одном
  режиме: сколько стоит цель — ваше решение, и выдумывать его за вас
  петля не станет ни в ту, ни в другую сторону.

Режим объявляется вслух — в шапке `run`/`go` и в `doctor` — и строка
называет ДЕЙСТВУЮЩИЕ потолки, а не имя режима: `money_bin` с одним явно
заданным числом это прогон С потолком, и говорить «потолков нет» было бы
ложью о вашей же настройке. Тихое «без ограничений» — это то, как
получают неожиданный счёт.

**Бюджет волны: общий пул и дисциплина экспериментов (правила владельца
2026-09-15, NXT-026).** Прогонные потолки (`total_budget_usd`, режим
`spending`) ограничивают ОДИН прогон. Поверх них действует бюджет программы
экспериментов, и правила у него свои:

- **Бюджет экспериментов — общий пул**, а не сумма по экспериментам. На
  текущую волну пул — **$60**; тратят его все запущенные эксперименты волны
  вместе.
- **Начатый эксперимент всегда доводится до конца.** Остановить на середине
  можно только по политике отказов (ниже) — не по «стало дорого»: оценка
  принимается до старта, а не пересматривается по ходу.
- **На границе пула новый эксперимент не стартует.** Старт возможен, только
  если остаток пула покрывает оценку эксперимента целиком; иначе эксперимент
  ждёт следующей волны или решения владельца.
- **Политика отказов: два подряд сбоя → диагностика → починка на ходу.**
  Подряд — значит подряд, без успешного вызова между. Починка на ходу
  делается в рамках того же эксперимента и фиксируется в findings. Если
  после диагностики починить на ходу нельзя — **эксперимент прерывается,
  владелец уведомляется**; решение о продолжении принимает он.
- **Перерасход пула — только с одобрения владельца.** Исчерпанный пул без
  такого одобрения означает: запущенное доводится до конца, нового не
  начинается.

**Фоновый замер: `[experiments] ambient`.** Эксперимент можно не
ставить стендом, а подмешать в обычную работу: фактор бросается жребием
на каждую задачу.

```toml
[experiments]
ambient = "tester"        # tester | memory_executor | memory_reviewer |
                          # memory_planner | skeleton
ambient_seed = 20260824   # без сида запись замера непроверяема
```

Что при этом происходит: на каждой задаче петля печатает
`фоновый замер: tester = on|off`, пишет в журнал `ambient_arm` и метрику
с фактором, плечом и сидом. Работа идёт настоящая. Разбор —
`python3 experiments/tools/ambient-report.py <стенд> [ещё стенды]`; он
откажется объявлять победителя, пока в меньшем плече меньше 8 задач, и
скажет, сколько ещё нужно.

Два отказа на старте, оба намеренные. Незнакомое имя фактора — отказ, а
не тихое «замер выключен». Фактор, который вы вместе с тем прибили явным
флагом (`ambient = "tester"` и `tester = true` одновременно), — тоже
отказ: журнал писал бы «выбрано жребием» о прогоне, где всё было решено
гвоздём, и заметить это удалось бы только через недели по несходящимся
числам.

**Когда петля — НЕ тот инструмент.** Если оставшийся зазор — это
ПЕРЕНОС решения, которое вы уже приняли, а не суждение, дописывайте
руками и закрывайте задачу как оператор (прецедент p1fn, ключ
`accepted_by`). Замерено на v9lb 2026-08-24: три раунда не смогли
вписать одну фразу, которую владелец потребовал дословно, — первый
раунд перевернул формулировку решения молча, второй сохранил
формулировку, но оставил болезнь непролеченной и фразу не вписал,
третий остановлен. Правка руками заняла минуты. Каждый следующий раунд
покупал ревью вашего собственного предложения.

Признак, по которому это видно заранее: в вердикте осталась ОДНА
находка, и она про отсутствие текста, который вы сами продиктовали.

**Записка `retry --note` — это тоже вход исполнителя.** Она попадает в
тот же промпт, что и ответы на вопросы, и с 2026-08-24 накапливается
вместе с ними, а не вместо них. До правки служебная записка («прогон
остановлен, вернул в очередь») занимала место принятых решений, и
следующий исполнитель получал уборочную заметку ВМЕСТО ответа владельца.
Пишите в `--note` то, что исполнителю полезно знать, а не то, что вы
делали с очередью.

**Дуэль: два исполнителя на задачу, парно.** Сильнее фонового жребия и
дороже его вдвое — это и был смысл просьбы «не про экономию».

```toml
[experiments]
duel = "memory_executor"   # тот же список факторов, что у ambient
ambient_seed = 20260824    # жребий берётся тот же
```

На каждой задаче петля печатает `дуэль <фактор>: живое плечо on,
теневое off (параллельно)` и делает так: ЖИВОЕ плечо работает в обычном
дереве, ровно как без флага; ТЕНЕВОЕ — в отдельном git-worktree под
`.swarm/arms/<задача>`, только чтобы быть измеренным. Работа теневого не
берётся НИКОГДА, даже если она выглядит лучше, — иначе замеряется отбор
лучшего из двух, а не каждое плечо. Живое плечо выбирается жребием
ЗАРАНЕЕ.

В журнале: `duel_start` (кто живой), `duel_shadow` (отчёт, гейт и объём
диффа теневого), метрика `phase="duel"`.

Что это стоит: два вызова исполнителя плюс второй гейт. Календарное
время растёт на один гейт, не вдвое, потому что исполнители идут
параллельно. **Предупреждение про железо:** два исполнителя на
Rust-проекте гоняют `cargo` каждый в своей сессии; на 8 ГБ это может
уйти в свап. Включайте на стенд и посмотрите на wall-time первой задачи,
прежде чем ставить на очередь.

**Пурист: развилки спецификации до работы.**

```toml
[experiments]
unclear = true
unclear_model = "claude:haiku"   # необязательно; по умолчанию движок исполнителя
```

Один короткий вызов на задачу ДО первого раунда. Отдаёт только список
решений, которых спецификация не принимает, — ответов не предлагает
намеренно. Список уезжает в промпт исполнителя с одним требованием:
если выбор всё же приходится сделать, назови его в `deviations`.

В выводе: `пурист: развилок спецификации N` или `пурист: спецификация
развилок не оставила` — второе законный и частый ответ, а не отказ.
В журнале — `unclear_found` со списком вопросов; метрика `phase="unclear"`.

Список НЕ уходит в инбокс: вопрос человеку на каждой задаче остановил бы
очередь целиком. Если развилка важна настолько, что работу продолжать
нельзя, это скажет сам исполнитель через `dispute` — канал для этого
уже есть.

**Потолок на вызов виден в журнале своим именем.** Когда исполнитель
упирается в `executor_budget_usd`, CLI выходит ненулевым кодом — по нему
это неотличимо от смерти процесса. Петля различает их по конверту:
обрыв по деньгам конверт ОСТАВЛЯЕТ и сам себя называет, настоящая
авария — нет. Поэтому в журнале стоит `budget_exhausted`, а не «крах», и
оператора не посылают искать аварию там, где надо поднять число. До
2026-08-24 стояло «крах»: разбор конверта был на ветке, которой не
бывает.

Опечатка в имени ключа не проходит молча: незнакомый ключ петля называет
в предупреждении при старте — иначе вы были бы уверены, что настройка
действует, а работало умолчание. То же и для значения флага памяти:
`[experiments] memory` — это имя роли, и `"planer"` вместо `"planner"`
выключил бы подсистему целиком, ничем не отличаясь от `off`. И то же для
`executor_engine`: незнакомое имя движка не становится умолчанием, а
останавливает прогон на старте — до первого потраченного доллара.

**`gate_command` — СПИСОК аргументов, не строка.** Строкой этот ключ
пишут чаще, и выглядит она естественнее, но петля запускает гейт без
шелла: строка целиком становится ИМЕНЕМ файла, и прогон падает
`FileNotFoundError` посреди первой задачи, объявив её аварийной. Форму
проверяют и `load_config` (предупреждение при старте), и `doctor`
(строка `[ПРОБЛ] gate`). Нужен шелл — `["sh", "-c", "…"]`, как в примере
выше.

**Два потолка раундов, а не один.** `max_iterations` тратит только
раунд, в котором работу РАССУДИЛИ: гейт вынес приговор или ревьюер вынес
вердикт. Раунд, сорвавшийся раньше — исполнитель умер по квоте или
таймауту, страж границ снёс работу, разъехались замороженные сигнатуры,
— судить было нечего, и лимит исправлений он не тратит: у него свой
потолок `max_futile_rounds`. В журнале это видно построчно
(`round_futile`: причина, деталь, «бесплодных N из M»), а эскалация по
исчерпании называет причину — `futile_rounds`, а не «раунды
исправлений кончились». До этого разделения петля объявляла задачу
слишком крупной за то, что случилось ДО первой оценки работы; на золотом
наборе пилота такой диагноз был неверен 6 раз из 6.

**Про деньги отдельно.** `review_budget_usd` — потолок на один вызов
ревьюера; на Rust-диффах $1.5 не хватало, потому что повторный проход
(после проверок исполнением) дороже первого. `total_budget_usd` — потолок
на весь прогон: петля считает траты по факту метрик и **останавливается
сама** — проверка стоит перед каждой итерацией, так что и одна
затянувшаяся задача не пробьёт потолок на много раундов. Если стоп
пришёлся посреди задачи, она не виновата: работа уходит в stash, задача
возвращается в очередь, и после поднятия бюджета прогон продолжается тем
же `go`. Обе цифры задаёте вы; без `total_budget_usd` ограничения нет
вовсе. Слепое пятно осталось, но оно про ДВИЖОК, а не про роль: Kimi не
сообщает стоимость своих вызовов, поэтому на `executor_engine = "kimi"`
траты исполнителя в счёт не входят. На движке `claude` цена известна из
конверта и в сумму входит — то есть тот же `total_budget_usd` теперь
ограничивает петлю целиком, и потолок достигается раньше, чем достигался
до этого. Если вы поменяли движок и прогон стал упираться в бюджет —
это не подорожание, а конец умолчания.

Перед первым прогоном прогрейте сборку (`cargo build`), иначе первая же
компиляция может упереться в `gate_timeout`.

**Что класть в гейт, кроме тестов.** Линт и проверку типов — не для
красоты. На самом оркестраторе при 538 зелёных тестах строгий `ruff` и
`mypy --strict` дали около полусотни содержательных находок, которых
тесты не находили: молча проглоченный битый конфиг, необработанный
`None`, адрес из переменной окружения без проверки схемы (§6.6). Порядок
внутри гейта — дешёвое раньше дорогого: линт, типы, тесты. Собственный
гейт роя устроен так же и живёт одной командой — `tools/swarm/check.sh`.

**Baseline должен быть зелёным.** Петля не запускает задачу на красном
гейте (§5.0) — и правильно делает: иначе исполнитель чинит чужую поломку
вместо своей задачи. Если в репозитории есть падающий тест, который вы
чинить не собираетесь, исключите его в `gate_command` явно и напишите в
комментарии почему.

### Готовые стенды

Развёрнутые конфигурации живут в `stands/<проект>/`: эталонный
`swarm.toml` плюс README с порядком развёртывания и списком мин, на
которых этот конкретный репозиторий подрывается.

- [`stands/cod-doc/`](stands/cod-doc/README.md) — Python-проект,
  ~1390 тестов, ruff + mypy strict, гейт 7 минут.

Что из этого стоит проверить на ЛЮБОМ новом стенде — четыре вопроса,
каждый из которых на cod-doc ответил «нет» и молчал до середины работы:

1. **Стенд ветвится от того, что вы считаете текущим состоянием?**
   Локальная ветка, ушедшая вперёд непушенного `origin`, — обычное дело;
   стенд от `origin/main` не содержит половины миграций, и падение
   выглядит регрессом исполнителя.
2. **У стенда СВОЙ venv (или его аналог)?** `pip install -e` привязан к
   тому дереву, где ставили: общий venv означает, что гейт судит чужой
   код. Проверяется одной строкой — `python -c "import <пакет>;
   print(<пакет>.__file__)"` обязан назвать путь стенда.
3. **Версии инструментов гейта закреплены?** Незакреплённый линтер — это
   движущийся гейт: свежая установка приносит правила, которых не было
   вчера, и baseline краснеет на нетронутом дереве. На cod-doc свежая
   установка дала 9 находок ruff и падение mypy на стабах numpy.
4. **Гейт стенда равен тому гейту, которому вы верите?** Локальный гейт
   и CI расходятся тихо: на cod-doc в CI ставится `.[dev]` со стабами
   типов, а в venv владельца их нет — и одна и та же строка кода даёт
   зелёное локально и красное в CI. Расхождение надо не устранять
   молча, а НАЗВАТЬ: работа, принятая роем, поедет в CI.

Пятое — не про стенд, а про имущество петли. `preflight` не стартует на
грязном дереве, а незакоммиченные `swarm.toml` и `.swarm/` для git —
грязь. Гонять каждый прогон с `--force` значит отключить защиту от
грязного дерева ради двух собственных файлов петли; чище убрать их в
`.git/info/exclude` целевого репозитория.

### MCP в Cursor и Kimi Code

Это не петля и не гейт. Два внешних MCP, которые агент в IDE вызывает
как инструменты: **cod-doc** (документы и задачи в БД, слаг `zairgrush`)
и **ai-reviewer** (превью ревью по диффу этого репозитория). Merge по
превью не блокируется — судья по-прежнему CI `pr-review`.

Конфиги:

- Cursor: [`.cursor/mcp.json`](.cursor/mcp.json) — `REVIEW_MCP_ROOT` задан
  абсолютным путём этого клона. `${workspaceFolder}` в MCP-процессе Cursor
  не раскрывается («No workspace folders found»).
- Kimi Code: [`.kimi-code/mcp.json`](.kimi-code/mcp.json) — те же серверы,
  корень задан абсолютным путём (Kimi не подставляет `${workspaceFolder}`).

Оба файла запускают `cod-doc-mcp --profile standard` абсолютным путём
к `.venv` клона `cod-doc` и лаунчеры `cursor-plugin/bin/*.sh` клона
`ai-reviewer`. После правки — **Developer: Reload Window**. В Cursor
новый сервер из проектного `mcp.json` нужно один раз подтвердить.

Плагин `cod-doc` в `~/.cursor/plugins/local` даёт skills и slash-команды;
MCP он не спавнит (рабочий namespace — `user-cod-doc` или проектный
`cod-doc`). Плагин `ai-reviewer` уже ставит те же два сервера глобально:
если в Customize видите красный `plugin-ai-reviewer-*` рядом с рабочим
проектным — оставьте проектный, глобальный можно выключить. Превью
смотрит в этот репозиторий, не в клон движка.

Проверка без перезагрузки IDE: `cod-doc connect doctor` (handshake
`cod-doc-mcp`) и в чате агента — `doc_list` / `review_prescan` по этому
корню.

## 2. Постановка задач

Задачи живут в `.swarm/tasks.json`. Их можно писать руками или получить
от планировщика.

### Планировщиком

```sh
swarm --root . plan --goal "Закрыть пробелы валидации в zeus-library" --dry-run
swarm --root . plan --goal "Закрыть пробелы валидации в zeus-library"
```

`--dry-run` показывает предложенный дифф, не применяя его. Планировщик
видит состояние репозитория и текущую очередь, а его выход механически
валидируется: уникальность id, обязательность `paths`/`acceptance`,
разрешимость `deps`, отсутствие циклов, отсутствие конфликтующих операций.
Невалидный дифф — одна повторная попытка, потом отказ.

**Границы задачи: спутники, которых план не замечает.** `swarm plan`
печатает под каждой задачей до шести строк вида

```
         ⚠ граница: zeus/crates/zeus-erc/src/engine.rs (erc01, erc02) —
           файл вне границ ссылается сразу на несколько файлов задачи:
           похоже на реестр или регистрацию (PILOT-1: q011)
```

Это СОВЕТ, а не запрет: ссылка — улика, а не доказательство, и решаете
вы. Основание прямое: семь оспоренных границ пилота из семи владелец
расширил, и каждый спор стоил раунда плюс ожидания ответа (медиана 24
минуты, худшее 21 час). Правится одной строкой в `paths` — до прогона,
а не после спора.

Чего линтер не умеет, чтобы вы не приняли молчание за гарантию: на том
же корпусе он называет 4 спорных файла из 7 (при потолке в шесть строк).
Класс «признак рождается выше по потоку — в импортёре» текстового следа
не оставляет вовсе и не ловится ничем механическим.

### Руками

```json
{
  "id": "v1we",
  "title": "wait_exponential: валидация аргументов",
  "type": "feature-tests",
  "status": "pending",
  "deps": [],
  "paths": ["tenacity/wait.py", "tests/test_swarm_validation.py"],
  "test_module": "tests/test_swarm_validation.py",
  "gate": "full",
  "spec": "wait_exponential молча принимает бессмысленные аргументы: min=10, max=5 создаётся без ошибки. Добавить проверку в __init__: min не больше max, multiplier положительный. При нарушении — ValueError с внятным сообщением, называющим параметр и значение.",
  "acceptance": [
    "весь существующий сьют проходит без изменений",
    "wait_exponential(min=10, max=5) возбуждает ValueError",
    "сообщения единообразны между стратегиями"
  ]
}
```

Поля, которые определяют поведение петли:

| поле | что делает |
| --- | --- |
| `type` | `feature` — правит код, тесты трогать нельзя; `feature-tests` — пишет свои тесты сам, чужие не трогает; `test-task` — правит только тесты; `idea` — заметка на будущее |
| `paths` | границы задачи. Проверяются механически по факту изменений; выход за них откатывается |
| `acceptance` | по ним судит ревьюер. Пишите проверяемые утверждения, а не пожелания |
| `deps` | порядок. Задача не берётся, пока зависимости не закрыты |
| `milestone_close` | включает проверки исполнением на этой задаче (при `verification = "milestone"`) |

### Что заходит хорошо, а что плохо

**Хорошо:** правка существующих файлов на 10–50 строк; один связный
результат; явные `paths` на конкретные файлы; критерии приёмки, которые
можно проверить командой.

**Плохо:** «отрефактори модуль» без описания результата; задачи, где
`acceptance` — это «код стал чище»; несколько несвязанных изменений в
одной задаче. Такие задачи выжигают лимит итераций, и диагност скажет
«слишком крупная, расщепить» — он будет прав.

**Осторожно:** создание новых файлов и каталогов. Механически это теперь
защищено (новый файл виден и ревьюеру, и проверке границ), но на живом
прогоне ещё не проверялось. Первые такие задачи стоит смотреть глазами
внимательнее обычного.

### Независимый эталон: пишите, чем сверять ЗАПРЕЩЕНО

Если задача требует сверить поведение с независимо посчитанным
результатом, критерия «сверять с независимым эталоном» **недостаточно**.
Для человека фраза однозначна, для исполнителя — нет: он ищет
кратчайший путь к зелёному тесту и берёт то, что проверяемый код уже
произвёл.

На пилоте это случилось дважды подряд с одним и тем же тестом. Сначала
эталон повторил форматную строку `location`, которую строит правило, —
ошибка форматирования не поймалась бы никогда. После исправления эталон
стал сверять по ключу подавления, который строит то же правило, — и
снова проверял реализацию против самой себя.

Поэтому перечисляйте запрещённые источники поимённо:

```
"сверка идёт по паре (SymbolId, Terminal.name), полученной обходом модели",
"в основу сравнения ЗАПРЕЩЕНО класть поля, которые вычисляет само правило:
 location, suppression_key и их производные (мультимножества, хеши)"
```

Правило продублировано в промпте планировщика, так что автоматически
составленные задачи его тоже несут.

## 3. Рабочий цикл

### От А до Я одной командой

```sh
swarm --root . go --goal "Закрыть пробелы валидации в zeus-library"
```

`go` — это весь цикл: рой **сам** декомпозирует цель в задачи (планировщик
внутри петли, а не человек снаружи), сам их исполняет по очереди и
останавливается только на том, что действительно требует вас: вопрос о
замысле, исчерпанный бюджет, авария. В конце печатает итог, стоимость и
путь к доске.

Повторный `go` без `--goal` продолжает незаконченную очередь — так
возвращаются после ответов на вопросы:

```sh
swarm --root . answer q003 "решение"
swarm --root . go                       # продолжает с того же места
```

Планирование пропускается, если в очереди есть незакрытые задачи. Если
при этом передать `--goal`, отличную от сохранённой, `go` откажется (код
2) и назовёт обе цели: раньше он молча доигрывал старый план под старой
вывеской, и доска показывала не ту цель. Продолжить старую очередь —
`go` без `--goal`; новая цель — сперва `swarm plan --goal "..."`.

Код возврата `run`/`go` — контракт для обёрток (полная таблица — в
`swarm --help`): `0` — все взятые задачи закрыты; `3` — нет готовых
задач; `4` — пауза по квоте провайдера; `11` — есть blocked/ask_user,
нужны вы; `12` — остановка по бюджету; `13` — исполнитель недоступен;
`2` — ошибка вызова. `swarm go && deploy` больше не «сработает» на
прогоне, вставшем по бюджету.

### Наблюдение

```sh
swarm --root . board --open    # доска: задачи, фазы, стоимость, вопросы
```

Одна страница, на которой видно всё: что сделано и чем закончилось,
сколько стоила каждая фаза, что вошло в код, где вас ждут (с готовой
командой ответа) и какие решения вы уже приняли.

Разделы идут по убыванию срочности, а не по алфавиту:

1. **Показатели.** Задачи (закрыто/заблокировано/в работе/в очереди),
   деньги — **по ролям** и против потолка `total_budget_usd`, если он
   задан; ревью (вердикты, approve против правок, вызовы без вердикта,
   находки по весу); гейт (доля зелёных) и цена контекста в токенах.
2. **Настоящее.** Что петля делает ПРЯМО СЕЙЧАС: фаза, задача, раунд,
   движок и модель, и сколько это уже длится (счётчик идёт сам). До
   этого блока страница молчала весь длинный вызов: и журнал, и метрики
   пишутся ПОСЛЕ фазы, так что семь минут работы исполнителя выглядели
   как тишина, а живой сервер исправно обновлял её тем же прошлым.
   Источник — `.swarm/now.json`; он существует, только пока фаза идёт.
3. **Ждут вас.** Вопросы петли и заблокированные задачи одним списком —
   и то и другое ждёт вас. У каждой строки готовая команда: `answer` для
   вопроса, `retry` и `why` для блокировки.
4. **События прогона** и **шаги без исхода** — как раньше, над списком.
5. **Ход прогона.** Шкала времени: строка — задача, отрезок — фаза
   (цвет = роль), засечка — фаза без измеренной длительности (гейт,
   границы). Наведение показывает время, деньги и исход; щелчок по имени
   задачи открывает её карточку. Топтание, ретраи и дорогое ревью видно
   формой, без чтения таблиц.
6. **Задачи** (поиск и фильтры; в строке — спарклайн находок по раундам)
   и **хроника**.

Если петля НЕ запущена, а отметка о фазе на диске осталась, доска не
называет это настоящим: она говорит «прогон оборвался на фазе …» и даёт
команду `resume`. Так и есть: `finally` при убийстве процесса не
отрабатывает, и переживший прогон файл — это место обрыва, а не работа.
Живость определяется захваченной блокировкой `.swarm/state.lock`, а не
pid из файла: pid переиспользуется системой.

Тема (светлая/тёмная) переключается кнопкой в шапке и запоминается
браузером; по умолчанию берётся системная.

Во время прогона доска по умолчанию — статический `.swarm/board.html`
(адрес `file://` в шапке). Живой HTTP-сервер — opt-in: `live_board =
true` в `swarm.toml`. Тогда `run`/`go` поднимают локальный HTTP-сервер
(адрес `http://127.0.0.1:<board_port>` печатается в шапке, macOS
открывает его в браузере сам; глушится отдельно: `board_open = false`),
и страница подтягивает свежие данные каждые несколько секунд БЕЗ
перезагрузки — раскрытые карточки, поиск, фильтр и прокрутка не
сбрасываются, в подвале тикает время последнего обновления. Когда прогон
завершается, страница честно пишет, что сервер остановлен, и замирает
на финальном состоянии. Порт задаётся ключом `board_port` (умолчание
7433); занятый порт не ломает прогон — сервер берёт свободный и печатает
фактический адрес.

Файл `.swarm/board.html` остаётся снимком на момент последней сборки —
его переписывает петля после каждого раунда, только если живая доска
включена (`live_board = true`), и он открывается без сервера в любой
момент. Посмотреть доску живьём вне прогона: `swarm board --serve`
(Ctrl+C — остановить).

Остановку прогона доска показывает сразу, без раскопок: блок «События
прогона» (исчерпанный бюджет, сорванное планирование) и блок «Шаги без
исхода — прогон падал» (интент коммита без записи о завершении, с
готовой командой `resume`) стоят над списком задач, а не в свёрнутой
хронике.

### Память между прогонами (E9, за флагом)

```sh
swarm --root . memory search "гейт cargo"   # уроки прошлых прогонов
swarm --root . memory add "текст" --anchor путь/файл   # урок вручную
swarm --root . memory reflect               # пересобрать LESSONS.md
swarm --root . memory sync                  # досыпать индекс: строки+вектора
swarm --root . memory reindex               # ПЕРЕСБОРКА индекса (DELETE+всё)
```

**Index maintenance is automatic when the stand opts in** with
`memory_index = "auto"` in `swarm.toml` (default `"manual"` — a run
with default config never touches the shared PG). With `auto`, the loop
runs `sync` itself on every terminal task outcome and again in the
after-run reflection: rows AND vectors catch up to the files, at most
64 embeddings per call, journal event `memory_synced` whenever vectors
were added. You never run `reindex` by hand anymore — it remains the
repair operation (full rebuild) for a corrupted index. Born from a
measured incident: an entire pilot produced ZERO embedder calls because
vectors only ever came from a manual `reindex` nobody ran. Embedder
calls are now metered in `helper-metrics.jsonl` from CLI paths too
(`helper: "embed"`, with provider-reported cost), so "was the embedder
used at all?" is answerable from the stand, not the provider dashboard.
For a calendar-based catch-up without runs (e.g. anchors drifting while
humans commit), schedule `swarm --root <stand> memory sync` via cron or
launchd — same code path, safe to run at any moment, including during a
live run (sync never deletes and never touches task state).

Петля сама пишет урок из каждого терминального исхода задачи (done —
урок, blocked — тупик с диагнозом, решения человека — принятое решение)
в `.swarm/memory/lessons.jsonl`; дайджест `LESSONS.md` пересобирается на
каждой записи. useful-урок без живого якоря (файл/коммит/задача)
отклоняется — память без якорей копит галлюцинации. Подмешивание уроков
в промпт включается флагом `[experiments] memory` в `swarm.toml`, и
значение флага — это ИМЯ РОЛИ: `off` (умолчание, промпты байт-в-байт
прежние), `executor`, `reviewer`, `planner`, `all`. Включайте по одной
роли: замер идёт по одному фактору за прогон, и `all` существует для
состояния «все роли уже померены поодиночке». Планировщик получает
уроки и в `plan`, и в `replan` — второе важнее: `replan` зовут ровно
после спора о границах, а прошлые споры и есть то, что вы уже решили.
Каждая инъекция видна в журнале (`memory_injected`: роль, сколько
уроков, какие id). Postgres — только поисковый индекс: он производный, уроки
целы в файлах, при недоступной базе поиск деградирует до локального
скана, а `reindex` лечит индекс одной командой.

### Вопрос, у которого не осталось адресата

Задачу можно вернуть в очередь двумя путями: ответом на вопрос
(`swarm answer`) и напрямую (`swarm retry`). Второй путь оставляет вопрос
без адресата — задача уходит работать и закрывается, а вопрос всё ещё
висит. Раньше это выглядело так: `swarm answer` отказывался принять
ответ ВМЕСТЕ С РАЗБОРОМ случившегося, а `swarm status` продолжал
печатать «очередь не пойдёт дальше без решения» над очередью, где всё
сделано (поймано на E13, задача b4wr).

Теперь такой вопрос называется устаревшим и ведёт себя честно:

- ответ на него **записывается** (в журнал и в решения задачи), но
  задачу НЕ переоткрывает — `swarm answer` прямо это говорит и называет
  `swarm retry <id>` как команду, которая переоткроет;
- решение остаётся при задаче: если её потом переоткроют, оно уйдёт
  исполнителю, а память (E9) строит из таких решений уроки;
- очередь он не держит: в `status` он показан отдельным списком
  «устаревшие вопросы», а строка «вас ждут N вопросов» считает только
  те, у которых задача жива;
- `swarm inbox` помечает его прямо в строке («задача закрыта — очередь
  не держит») и считает отдельно.

Что НЕ изменилось: ответ по-прежнему не воскрешает закрытую задачу
(безусловный возврат в очередь отправлял бы готовую работу на повторное
исполнение), и повторный ответ на один вопрос по-прежнему отказ.

### Ревью, которое не прошло контракт

В журнале и на доске могут встретиться две строки, которых раньше не было.

`вердикт добыт из потока` (`verdict_salvaged`) — конверт ревьюера пришёл
пустым, а суждение осталось в потоке вызова, и петля его оттуда достала.
Это не «почти вердикт»: восстановленное проходит ту же проверку, что и
любое другое, и негодное отвергается так же. Строка нужна затем, чтобы
вы могли отличить обычное ревью от того, где сработало спасение, — если
таких строк много, дело в модели ревьюера, а не в коде.

`повтор` в промпте второго вызова — петля теперь называет ревьюеру
причину, по которой отвергла первый ответ (`analysis короче 40 символов
— это заглушка, а не разбор» и подобные). Первый вызов не изменился ни
на байт: причина живёт в самом хвосте промпта, чтобы не обнулять кэш.

Откуда это: на бенче E13 пять вызовов ревьюера из семнадцати не дали
валидного вердикта и стоили $0.67 — 37 % всех денег ревью. Половина
случаев — ответ-заглушка (`analysis: "Test"` при `verdict: approve`),
и ловит её порог существенности; половина — вердикт, сложенный моделью
в одно поле, который теперь возвращается вместо того, чтобы пропасть.

Ещё одно следствие: поток отказавшего ревью больше не затирается. Задача,
возвращённая в очередь через `swarm retry`, начинает раунды заново и
раньше писала в тот же файл — на E13 так исчезла улика единственного
отказа, который и надо было разбирать. Конверт остаётся под прежним
именем, поток уходит в соседнее (`…-review-stream-2.jsonl`), и глоб
`*-review-stream*.jsonl` ловит их все.

### Куда смотреть, когда прогон встал

```sh
swarm --root . why            # задача, которая первой требует внимания
swarm --root . why v2wf       # разбор конкретной задачи
```

`why` собирает в один ответ то, что раньше приходилось складывать из
пяти мест: статус и причину блокировки, собственный диагноз петли,
траекторию раундов с прочтением («находки убывают» / «стоит на месте —
это топтание»), последний вердикт ревьюера с находками, открытый вопрос,
метку stash с сохранённой работой, пути к сырым логам — и готовые
команды, которыми это разбирается. Это первое, что стоит запускать: не
`status`, а `why`.

`status` тоже заканчивается строкой «дальше» с одной конкретной командой
под текущее состояние очереди.

### Осторожный режим

```sh
swarm --root . status          # что в очереди, сколько потрачено
swarm --root . run --limit 1   # одна задача за прогон
```

Имеет смысл, пока доверие к постановке не сложилось, и на классах задач,
которые ещё не проверены живым прогоном (создание модулей).

Прогон заканчивается одним из исходов:

- **done** — задача закрыта и закоммичена. Смотрите `git log -p`.
- **ask_user** — есть находка о замысле, петля спрашивает вас.
- **blocked** — спор исполнителя, нарушение границ, исчерпание раундов,
  авария или нарушение доверия.

Во всех неудачных случаях работа не теряется: она уходит в `git stash` с
меткой, а задача получает вопрос в инбоксе.

### Разбор вопросов

```sh
swarm --root . inbox
swarm --root . answer q003 "текст решения"
swarm --root . answer q003 "текст решения" --add-path src/utils.rs
```

Отвечайте по существу замысла, а не по механике: механические находки
исполнитель чинит сам, вам приносят только то, что требует решения. Ответы
**накапливаются** — второй не затирает первый, и все они видны и
исполнителю, и ревьюеру в последующих раундах.

`--add-path` нужен, когда ваше решение требует тронуть файл вне границ
задачи. Без него исполнитель упрётся в проверку границ и будет откатан —
это уже случалось на приёмке: указание «вынеси в `_utils.py`» было
невыполнимо, потому что `_utils.py` не было в `paths`.

### Повторяющиеся замечания

Если ревьюер раз за разом требует одного и того же, а вы это решение уже
отклонили, — заведите политику прогона:

```sh
swarm --root . policy add "Release notes вне scope этого прогона" --match "release note" --match "reno"
swarm --root . policy list
```

Политика фильтрует находки **на стороне оркестратора**, а не затыкает
ревьюера: он продолжает сообщать всё, подавленное видно в `policy list` и
в отчёте. `blocker` не подавляется никогда — политика снимает требования к
оформлению, но не к корректности. Политика умирает вместе с целью прогона.

### Застрявшая задача

```sh
swarm --root . retry v2wf --note "указание, что делать иначе"
```

`retry` принимает задачи в `blocked` и в `in_progress` (вторая — когда
прогон умер на сбое).

## 4. Когда что-то идёт не так

**Первое правило: подозревайте обвязку, а не модель.** За всю программу
найдено 24 дефекта — все в оркестраторе, ни одного нарушения контрактов
моделями. Трижды подряд автоматический диагноз говорил «задача слишком
крупная», а виноваты были гейт без линтера, механика подтверждения и
парсер отчёта.

Порядок диагностики:

```sh
swarm --root . why v2wf               # почему встала и что нажать дальше
swarm --root . report --task v2wf     # хроника задачи связным текстом
swarm --root . report --task v2wf --json   # то же сырьём, без обрезки
cat .swarm/metrics.jsonl              # фазы, длительности, стоимость
ls .swarm/log/                        # сырые ответы агентов по итерациям
```

`report` печатает журнал фразами и группирует записи по задачам; события
прогона (бюджет, план, preflight) идут отдельным блоком «прогон в целом»
— они ничьи, и приклеенные к задаче объясняли бы остановку очереди не тем.
Ни одно поле записи не теряется: то, что не вошло во фразу, дописывается
хвостом `ключ=значение`. Если нужен точный первоисточник — `--json` даёт
те же строки без обрезки.

В `.swarm/log/` лежат `<task>-i<N>-executor.jsonl` (поток исполнителя),
`<task>-i<N>-a<M>-review.json` (конверт ответа ревьюера; фаза `v` —
повторный проход после проверок исполнением) и рядом
`<task>-i<N>-a<M>-review-stream.jsonl` — полный поток ревьюера. Если
поведение непонятно — читайте их раньше, чем правите постановку.

Типичные картины:

| симптом | где смотреть |
| --- | --- |
| задача не сходится за лимит | вердикты ревьюера: он требует чего-то, что исполнитель не может проверить? добавьте это в гейт |
| `no_report` подряд | поток исполнителя: он отвечает, но не по контракту? |
| «нарушение доверия» | исполнитель тронул историю или `.swarm/`; смотрите `integrity_violation` в журнале |
| авария прогона | `task_crashed` в журнале, работа в stash, задача в `blocked` |
| раунд «впустую», `round_futile` с `detail=budget_exhausted` | исполнитель упёрся в `executor_budget_usd` (потолок на ОДИН вызов) до того, как вернул отчёт. Его правки на диске ЦЕЛЫ, и следующий раунд получает совет продолжить с них, а не начинать заново. Лимит раундов такой раунд не тратит. Лечится поднятием потолка или дроблением задачи — но сначала посмотрите на дифф: упор в потолок часто значит, что задача крупнее, чем выглядела |
| пауза по квоте | `quota_wait`/`quota_pause` в журнале (ревью) или reason="quota" в plan-metrics.jsonl (планирование); задача в `pending`, работа в stash — переждите и повторите `go` |
| планировщик молчит дольше plan_timeout | вызов остановлен, причина `timeout` в plan-metrics.jsonl; один повтор делается сам, дальше — поднять `plan_timeout` или сузить цель |

**Коды возврата.** `0` — все взятые задачи закрыты; `2` — отказ,
требующий вашего решения (preflight, эскалация resume, противоречивое
состояние, `--goal` не совпала с сохранённой); `3` — нет задач, готовых
к запуску; `4` — пауза по квоте провайдера: петля подождала по
нарастающей (`quota_backoff_s`), квота не отпустила, задача возвращена в
очередь — повторите `go`, когда лимит сбросится; `11` — есть исходы
blocked/ask_user, разбирайте инбокс; `12` — остановка по бюджету
прогона; `13` — исполнитель недоступен (мгновенные аварии процесса —
смотрите stderr в журнале, `executor_failed`).

**`swarm resume` после падения.** Незавершённый шаг коммита resume
разбирает сам: в intent-записи лежит `head` до действия, и по истории
видно, состоялся ли коммит. Коммита не было — задача возвращается в
очередь; коммит оркестратора найден — задача закрывается им. Требовать
`--force` resume продолжает только там, где механически решить нельзя:
интент старого формата без `head` или чужой коммит поверх.
`resume --dry-run` показывает, ЧТО будет сделано, не трогая ни журнал,
ни очередь.

**Восстановление работы из stash.** Метка вида `swarm:v3st-max-iterations`
видна в `git stash list` и в поле `stash` задачи. Петля сама её не
применяет — это ваше решение.

## 5. Что смотреть глазами

Инструмент проверяет механику: тесты, границы, формат контрактов,
неизменность истории. Он не проверяет замысел. Ваш просмотр —
единственное место, где ловится «сделано правильно, но не то».

Минимум на каждый коммит: `git log -p -1`. На что смотреть в первую
очередь — на соответствие `acceptance` и на то, не решена ли задача
формально (проверка добавлена так, что тест проходит, а смысла нет).

Раз в несколько задач полезно:

```sh
swarm --root . map --budget 40      # карта символов: не расползлась ли структура
swarm --root . impact <symbol>      # кто зовёт символ перед его правкой
```

## 6. Границы применимости

Что система делает надёжно: правки существующего кода по чётким критериям,
с полным сьютом в гейте, на проектах масштаба нескольких тысяч файлов.

Что не проверено: создание модулей на живом прогоне; проекты в 10–100 раз
крупнее приёмочного стенда; языки без точного индекса (индекс символов
сделан для Python, для Rust работает tree-sitter приблизительно);
параллельные пары на разных worktree.

Что не сделано: изоляция исполнителя. Пост-проверка ловит изменение
истории, правку состояния петли и незавершённые rebase/merge, но не
помешает агенту прочитать `.env`. Отсюда требование отдельного клона в
§1 — оно не формальность.
