
# ADR-029: Пакетное ревью по майлстоуну: одно ревью на секцию плана вместо ревью на задачу

| Поле | Значение |
|------|----------|
| **Статус** | ✅ accepted |
| **Дата** | 2026-11-18 |
| **Автор** | dakh |

## Контекст

Полевая сессия ZeusLogic 2026-09-20 (15-field-audit-zeuslogic.md), 17 задач, метрики стенда ~/work/zeus-pilot/.swarm/metrics.jsonl. Время / деньги по шагам: исполнитель 16 698 с / $32.19; пурист `unclear` 3 393 с / $5.82; первое ревью (19 вызовов) 2 858 с / $29.24; подтверждающее ревью (16 вызовов) 1 803 с / $10.14. Ревью — 68 % денег петли ($39.38 из $58). Стоимость ревью почти не зависит от диффа: 38 строк стоили $0.82 (246k токенов cache-read), 1114 строк — $1.82. Ревьюер перечитывает контекст репозитория при каждом вызове, и эта цена платится на каждую задачу. Подтверждающее повторное ревью (`confirmations = 2`) изменило исход один раз на 16 вызовов. Ревью стоит на критическом пути: следующая задача ждёт вердикта по предыдущей.

## Решение

1. Новый ключ swarm.toml `review_mode = "task" | "batch"`, умолчание `task` — поведение не меняется. Ключ `batch_max_lines` (умолчание 1500). 2. Единица пакета — `milestone` задачи (секция плана, обычно один модуль). Выбрано владельцем вместо «каждые N задач»: секция даёт связный дифф. 3. В режиме batch задача без риска проходит gate/integrity/scope/signatures, коммитится, получает `done` с `review_pending = <milestone>` и событие журнала `review_deferred`. 4. Пакет ревьюится, когда в майлстоуне не осталось работы в pending/in_progress/in_review (blocked не удерживает), либо дифф пакета превысил `batch_max_lines`, либо очередь кончилась. Один вызов ревью; дифф — от родителя старшего коммита пакета до HEAD, ограничен файлами, тронутыми коммитами пакета; ревьюер дополнительно получает `git show`/`git log`. Сначала gate на HEAD; красный = пакет не ревьюится. 5. Каждая находка несёт необязательное поле `task` (новое опциональное поле схемы verdict-v1); запасная атрибуция — последний коммит пакета, тронувший файл, иначе последняя задача. 6. approve снимает метки. request_changes/blocked — по одной fix-задаче на задачу с находками (`fix_of`, `review = "task"`, тот же milestone, paths + файлы находок), ревьюятся сразу; intent-находки и `blocked` создают fix-задачу в blocked с вопросом в inbox. 7. Сразу, минуя пакет, ревьюятся: задача без milestone, fix-задачи, диффы по защищённым путям или манифестам зависимостей (те же охранные условия, что в триаже ADR-027). 8. Отдельной staging-ветки нет: петля не пушит (дизайн-док §5.4, push — человек), локальная история и есть staging; `swarm status` показывает «ЖДУТ ПАКЕТНОГО РЕВЬЮ». 9. Упавшее пакетное ревью оставляет метки; одна попытка на пакет за прогон; следующий `swarm go` повторяет.

## Альтернативы

(i) Пакет «каждые N задач» — проще, но смешивает несвязанные изменения в одном диффе. (ii) Только `confirmations = 1` — убирает ~$10 и ~30 мин на сессию, но оставляет фиксированную цену на задачу и критический путь. (iii) Отдельная ветка `swarm/batch-N`, вливаемая после approve — избыточна: петля не пушит.

## Последствия

+ Проекция для той сессии: ~$15–18 вместо $39 и ~1 500 с ревью вместо ~4 700 с, вне критического пути. Это проекция, не замер; замером станет первая сессия в режиме batch по тем же метрикам. − Находка, пойманная в пакете, ложится поверх поздних задач, уже построенных на ней; переделка дороже. Ограничено `batch_max_lines`, немедленным ревью рискованных диффов и gate на каждой задаче. − Локально существует закоммиченная, но не отревьюенная работа; человек не должен пушить майлстоун с метками `review_pending`.
