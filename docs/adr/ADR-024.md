
# ADR-024: память между прогонами: файлы первичны, PG — индекс, FTS ведёт

| Поле | Значение |
|------|----------|
| **Статус** | ✅ accepted |
| **Дата** | 2026-08-23 |
| **Автор** | cursor-grok |

## Контекст

E9 вводит память между прогонами: уроки прошлых задач подмешиваются в промпт. Подсистема собрана этапами, плечо планировщика измерено. Решения об устройстве жили в комментариях кода и в плане: что первично при падении Postgres, нужен ли pip-драйвер, кто ведёт поиск — FTS или вектор, строить ли ANN на десятках строк.

Правило петли: состояние переживает потерю чего угодно, кроме git. Память — такое же состояние, как журнал и очередь. Отдельная «база как правда» ломает это правило в момент, когда PG недоступен.

Запись ADR-013 это уже приняла (2026-08-23), но alternatives были пусты, а решение разрослось в устройство подсистемы вместе с багфиксом FTS. Решение не меняется; меняется запись. Ссылка на журнал — ADR-015, не ADR-001.

## Решение

Файлы — источник истины памяти. PostgreSQL — производный индекс.

- `.swarm/memory/lessons.jsonl` (append-only) и детерминированный `LESSONS.md`. Строки в PG пересобираются `swarm memory reindex`.
- Клиент PG — `psql` через subprocess, не библиотека. Запросы через одну `pg()`; данные — `-v` и `COPY FROM STDIN`; интерполяция в SQL запрещена и покрыта мутациями.
- FTS ведёт (`websearch_to_tsquery` из значимых слов через `or`, не AND по всей спеке). Вектор дописывает хиты сверх FTS без RRF и реранкеров.
- ANN-индекса нет: sequential scan на десятках-сотнях строк. IVFFlat/HNSW на таком объёме — обслуживание без выигрыша, особенно при смене эмбеддера.
- Каждая строка несёт `repo` и `stand`. Retrieval фильтрует по `repo`; `reindex` чистит только свой `stand`.
- Grounding как пропуск: `useful` без живого якоря отклоняется. Устаревание — ре-валидация якорей, не TTL. `dead_end` — первоклассный исход наряду с `useful`.

Не выбрано: PG-первичность; pip-драйвер; вектор как основной ретривер; ANN.

## Альтернативы

**A. PostgreSQL — источник истины, файлы — экспорт.**
Отвергнут: crash-safety петли файловая (ADR-015). «Упал постгрес» при PG-первичности — потеря уроков; при файловой — деградация поиска. A/B требует снапшота памяти перед плечом: каталог файлов снапшотится тривиально.

**B. Клиент PG — библиотека Python (psycopg и т.п.).**
Отвергнут: первый pip-пакет меняет установку инструмента у всех. Петля и так живёт процессами (kimi, claude, git, ctags). `psql` + `COPY FROM STDIN` + `-v` без интерполяции в SQL; цена — процесс на запрос, на сотнях уроков незаметна.

**C. Вектор ведёт, FTS как добавка (или наоборот на бумаге при AND-запросе).**
Отвергнут в той форме, в какой жило: `websearch_to_tsquery` AND по всей спеке давал 0 строк, вектор — 100 % хитов. После OR значимых слов на 16 запросах FTS 65/80, вектор 15 сверх. Реранкеры у оракула только вредили — не берём.

**D. Файлы первичны, `psql` subprocess, FTS ведёт, вектор добавляет, ANN нет.**
Принят.

## Последствия

**Плюсы**
- Потеря PG стоит качества поиска, не данных; `reindex` идемпотентен.
- Установка петли без pip-зависимостей памяти.
- E6 получил ответ: эмбеддинги нужны как добавка (15/80), не как основной ретривер.

**Минусы**
- `psql` на процесс — потолок, если корпус вырастет на порядки.
- Стеммер `russian` ломается на идентификаторах кода; вектор это частично закрывает.
- Эмбеддер внешний (OpenRouter); Ollama Cloud эмбеддингов не даёт. Недоступность → деградация до FTS, не падение.

**Что осталось**
- Решение об инъекции в промпт здесь не принимается. Измерено плечо планировщика; исполнитель и ревьюер ждут прогоняемой очереди. E9 открыт.
- Телеметрия `queries.jsonl` пишется настоящим путём поиска: реплей retrieval обязан снимать файл, иначе синтетика смешается с фактом.
