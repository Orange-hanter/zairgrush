
# ADR-021: инбокс и триаж: вопрос человеку не останавливает прогон

| Поле | Значение |
|------|----------|
| **Статус** | ✅ accepted |
| **Дата** | 2026-08-08 |
| **Автор** | cursor-grok |

## Контекст

До этого петля знала два исхода: закрыть задачу или заблокировать её. Любая блокировка останавливала прогон и требовала человека немедленно. «Переименуй переменную» и «эта абстракция лишняя» шли одним путём, хотя первое — механика, второе — замысел автора.

FuguNano на похожей архитектуре развёл триаж находок, отложенный вопрос, keep-best и диагноз несходимости. Нужно было взять это, не превращая человека в синхронный шаг каждой итерации.

Запись ADR-009 это уже приняла (2026-08-08), но alternatives были пусты, а приёмка tenacity жила в последствиях как часть решения. Решение не меняется; меняется запись.

## Решение

Человека дёргают только по замыслу; прогон из-за вопроса не останавливается.

- Триаж: категории `architecture` и `scope` — замысел; явное `intent` сильнее категории. Механика уходит исполнителю в тот же раунд.
- Первый approve даёт `CONFIRM`, не `DONE`. Нужны два независимых подтверждения (настраивается).
- Keep-best: раунд с наименьшим числом находок запоминается; худший следующий откатывает worktree. Цикл не деградирует.
- Несходимость эскалирует с диагнозом из закрытого списка (неясное требование, ревьюер строже спеки, качели fix→break, задача слишком крупная) — не новым кругом.
- Инбокс: `swarm inbox` / `swarm answer`. Вопрос откладывается, петля берёт следующую задачу. Ответ возвращает задачу в очередь и кладёт решение в handoff как обязательное. Источники: находки о замысле, эскалации, споры исполнителя.
- Коды `loop.decide`: `0` готово, `10` петля работает сама, `11` нужен ответ по замыслу, `20` разбирается человеком целиком.

Не выбрано: стоп прогона на любой блок; закрытие с одного approve.

## Альтернативы

**A. Любая блокировка останавливает прогон.**
Отвергнут: «переименуй переменную» и «эта абстракция лишняя» обрабатывались одинаково. Первое чинит исполнитель, второе знает только автор. Человек становился синхронным барьером всей очереди.

**B. Один approve закрывает задачу.**
Отвергнут: верификация вероятностна. На tenacity первый approve ушёл в CONFIRM и закрытие пришло вторым независимым подтверждением.

**C. При несходимости ещё один круг без диагноза.**
Отвергнут: замечания одного класса, которые не убывают, крутятся бесконечно. Нужен закрытый список причин и эскалация, не ещё одна итерация.

**D. Триаж + инбокс + keep-best + двойное подтверждение.**
Принят. Приёмка на tenacity (2043 строки, 178 тестов): человека выделили 1–2 находки из 6–7, петля закрыла одну задачу, две отложила и не встала.

## Последствия

**Плюсы**
- Человека дёргают реже и по замыслу. Одна спорная задача не блокирует очередь.
- Внешний скрипт читает коды `loop.decide` (0/10/11/20), а не парсит прозу.

**Минусы**
- Триаж по категориям — эвристика: механическую находку можно назвать архитектурной. Цена ошибки — один лишний вопрос; поле `intent` сильнее категории.
- Два подтверждения удлиняют путь минимум на один вызов ревьюера (на приёмке ~$1 из $5).

**Что осталось**
- Коды процесса CLI (бюджет, нет исполнителя, пустая очередь) — отдельный слой, не подмена 0/10/11/20.
