# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это за репозиторий

Это **самостоятельный проект ZAIrgRush** (GitHub: `Orange-hanter/zairgrush`) —
референсная реализация «роя агентов» для мультиагентной петли разработки, где
Kimi Code (исполнитель, модель K3) и Claude Code (ревьюер) обмениваются
задачами через тонкий Python-оркестратор. Раньше каталог был рабочим
пространством только документации проекта ZeusLogic; реализация (`tools/swarm`)
с тех пор переехала сюда же и стала полноценным кодом с тестами — документация
и реализация теперь живут в одном репозитории. Файлы:

- `05-agent-swarm.md` — основной дизайн-док петли (версионируется, см. журнал изменений);
- `05-agent-swarm-audit.md` — отчёт аудита v0.4 с обоснованиями и источниками решений, вошедших в v0.5+;
- `06-knowledge-infra-experiments.md` — программа экспериментов над знаниевой инфраструктурой (дублирующие варианты подсистем E1–E8, протокол findings/ADR);
- `07-experiments-journal.md` — связный журнал программы экспериментов (человекочитаемая проза по фактам из `experiments/`);
- `08-operators-guide.md` — руководство оператора петли (что делать руками, по факту поведения инструмента);
- `11-architecture-diagrams.md` — архитектура в диаграммах Mermaid (роли, потоки данных, цепочка гейтов, учёт раундов, контракт вердикта, эскалации, память); документ на английском, диаграммы проверены рендером `mmdc`;
- `tools/swarm/` — сама реализация: CLI `swarm`, оркестратор, индексация кода, тесты (`pytest`, `tools/swarm/tests/`), JSON-схемы контрактов (`tools/swarm/schemas/`);
- `experiments/adr/` — принятые решения экспериментальной программы (ADR); `experiments/findings.jsonl` — сырой журнал наблюдений. Рабочие стенды экспериментов (`experiments/stand*`, `bench/`, `repomap/` и т.п.) — воспроизводимый scratch, в git не попадают (`.gitignore`).

Сборка/линт не настроены; тесты — `cd tools/swarm && python3 -m pytest`.

## Ключевые идеи документа (контекст для правок)

- **Агенты stateless, состояние в файлах** (`.swarm/tasks.json`, `state.json`, журнал) и в git; петля строится из коротких свежих запусков `kimi -p` / `claude -p`, а не из долгоживущих сессий.
- Три дорогие роли: исполнитель (Kimi), ревьюер (Claude, строго read-only), планировщик (Claude, меняет план только через валидируемый план-дифф). Плюс третий контур — опциональные хелперы на дешёвых моделях.
- Контракты обмена — строгий JSON: verdict ревьюера с закрытыми enum'ами severity/category (§12), отчёт исполнителя с каналом dispute. Оркестратор валидирует всё механически; невалидный ответ = один retry, затем эскалация человеку.
- Оркестратор «тупой»: сам запускает тесты (gate), проверяет scope по diff, коммитит после approve, следит за стоп-условиями (max_iterations, детект топтания, бюджет).

## Приоритет документации

Документация — всегда в приоритете (§3.3 в 05-agent-swarm.md): рабочая
сессия не закончена, пока затронутые доки не актуализированы (frontmatter,
журнал изменений, статусы в 06-доке, findings/отчёты в experiments/). Для
развёрнутых человекочитаемых текстов (журнал программы, ADR-проза,
отчёты) спавнь отдельного агента-документатора: подробная связная
инженерная проза для человека; вход агента — структурные данные
(experiments/*.jsonl, raw/, metrics), не пересказы из контекста.

## Конвенции работы с документом

- Язык документа — русский; технические термины, названия CLI-флагов и JSON-поля — на английском, как в тексте.
- YAML-frontmatter: при содержательной правке обнови `version` (схема 0.x) и `updated` (дата ISO); статус пока `draft`.
- Каждое изменение версии фиксируй записью в разделе «Журнал изменений» в конце файла — по образцу существующих записей v0.1–v0.4, новые версии сверху.
- Внутренние перекрёстные ссылки — через номера секций в формате `§N.M`. При добавлении/удалении секций проверь, что существующие `§`-ссылки не сломались.
- Ссылки в frontmatter `related:` (docs/00-conventions.md, docs/01-requirements.md) указывают на документы репозитория ZeusLogic и в этом каталоге не существуют — это не ошибка.
- Пометки «на утверждение» / «проект значений» (таксономия §12, пороги §9.1) означают открытые решения: не убирай их без явного подтверждения пользователя, что решение принято.
